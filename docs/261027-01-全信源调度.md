# 全信源统一调度：封面 / 头像 / 歌词 / 艺术家信息（261027-01）

> 用户原话（261026-05 / 261026-06 / 261025-02 反复要求）：
> 「头像问题，这个问题非常离谱，我们的所有接入的数据源，应该是通用于封面、头像、歌词、艺术家等等
> 所有内容收集，不存在某个源只提供一种信息的情况。头像也不应该仅接入网易云一个信源，应该是全信源
> 接入。请你核查你当前信源的使用到底是怎么回事，谁告诉你直接入一个信源的。请你不要偷懒！」

本轮要解决的不是「哪个源漏了」，而是**「谁能提供什么」这件事从来没有被声明过**。

---

## 1. 核查：老代码为什么只接网易云

真因不是疏忽，是**结构**：能力只有两个布尔位，头像根本没有对应的位。

| 位置 | 老形态 | 后果 |
|---|---|---|
| `src/meta/provider.h:1482` `provider_registry()` | 每个源只有 `canSearch` / `canLyric` 两个 bool | 「能不能出封面/头像/简介」无处声明，只能靠「某人当初写了哪段代码」 |
| `tools/rtaweb.cpp:4270` `artist_avatar_fetch` | 硬编码 `POST music.163.com/api/search/get type=100 limit=1` → 抠第一个 `picUrl` | 头像**只有网易云**；且 `limit=1` + 不校验名字 ⟹ 会贴错人（粉丝号） |
| `src/meta/enrich.h:439` 封面段 | 只取 `best.coverUrl` 一张 | 首选候选的图 404/超时 = 整首没封面，别的候选/别的源有图也不用 |
| `src/meta/enrich.h:472` 歌词段 | 手写 `provider_registry().rbegin()` + `canLyric` 过滤 | 与注册表顺序耦合，新增源要改循环 |
| `src/meta/provider.h`（6 个源） | 头像能力完全没有声明 | `/api/providers`、设置页也不知道谁能出头像 |

**结论：老设计里「某个源只提供一种信息」不是事实，是声明缺失导致的实现缺失。**

## 2. 能力矩阵（唯一的「谁能干什么」事实源）

`ProviderDesc.caps`（`src/meta/provider.h`）= 7 个能力位：
`Cover / ArtistImage / Lyrics / ArtistBio / ArtistLink / TrackMeta / Search`。
`canSearch`/`canLyric` 现在是**派生视图**（`caps & 指针`），不再是第二份事实源 —— 有单测断言。

每格都对应真实接口与实测（2026-10-27，匿名、本机真实网络）：

| 源 | 封面 | 头像 | 歌词 | 艺人简介 | 艺人外链 | 曲目元数据 | 证据 |
|---|---|---|---|---|---|---|---|
| **dizzylab** | ✅ | ✅ | ❌ | ✅ | ✅ | ✅ | 封面 `cdn.dizzylab.net/media/cover/<catalog>.jpg!cover`(provider.h 616)；头像 = `GET /search/?s=` **「用户」段**卡片里的 `avatars/…!cover`（实测 Khrisma 68,713 B / 熊青嵐 60,009 B / 风宇 41,991 B）；简介 = 同卡片的 `<p>`（实测「月華社所属。东方/编曲…」）；外链 `/u/<id>`。**无歌词接口**（站点没有歌词，如实填 false） |
| **QQ** | ✅ | ✅ | ✅ | ❌ | ✅ | ✅ | 封面 `y.gtimg.cn/.../T002R800x800M000<album.mid>.jpg`；头像 = `POST musicu.fcg` `search_type=1` 歌手搜索 → `singerMID`+`singerPic`（实测 蔡琴 17,197 B / TAMUSIC 49,625 B / 初音未来 23,951 B / 倉木麻衣 33,872 B）；歌词 `GetPlayLyricInfo`（已验证）；**简介无公开接口** ⟹ false；外链 `y.qq.com/n/ryqq/singer/<mid>` |
| **网易云** | ✅ | ✅ | ✅ | ❌ | ✅ | ✅ | 封面 `album.picUrl`；头像 = `type=100` 的 `artists[].picUrl`（实测 蔡琴）；**简介 false**：`/api/artist/{id}` 的 `briefDesc` 对 蔡琴/周杰伦/北京梵乐团 三个 id 实测返回 200 但长度 0，正文要 weapi 登录态 ⟹ 未找到公开接口 |
| **iTunes** | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ | 封面 `artworkUrl100`→`1200x1200bb`；**头像 false**（实测 `entity=musicArtist` 的 results 只有 artistName/artistLinkUrl/artistId/primaryGenreName，**没有 artwork 字段**，响应 671 B）；外链 `artistLinkUrl` |
| **lrclib** | ❌ | ❌ | ✅ | ❌ | ❌ | ❌ | 只有 `/api/get`+`/api/search` 歌词 |
| **Discogs** | ✅ | ✅ | ❌ | ✅ | ✅ | ✅ | 封面 `/releases/{id}`.images[]；头像 `/artists/{id}`.images[]（实测 蔡琴 600×600 / Liz Mitchell 204×249）；简介 = 同响应的 `profile`（实测「Tsai Chin (Pinyin: Cài Qín) is a pop and folk singer from Taiwan…」）；外链 `uri`。**匿名限频 25/min**（本轮实测被 429）⟹ 内部 2.5 s 节流 + 429 后全源冷却 300 s |

**填 false 的三处，都是「未找到公开接口/字段实测为空」，不是懒得做**：iTunes 头像、网易简介、QQ 简介。

## 3. 改造：候选列表从矩阵派生（数据驱动）

新增 `src/meta/artwork.h`（header-only），三类内容只有一个入口：

```
art_cover_sources()   Cover 位 + 注册表正序     = dizzylab,qq,netease,itunes,discogs
art_artist_sources()  ArtistImage 位 + 正序     = dizzylab,qq,netease,discogs
art_lyric_sources()   Lyrics 位 + **逆序**      = lrclib,netease,qq   （与原顺序逐项相同）
art_artist_image_plan() = 上者 ∩ 抓取实现表     （声明了能力却没实现 ⟹ 单测直接红）
```

* 新增一个源 = 在 `provider_registry()` 声明 caps + 在 `art_artist_fetchers()` 注册实现，**不改任何循环**；
* `enrich.h` 的歌词段/封面段已改为调用派生列表（`art_lyric_sources` / `art_cover_urls_by_score`）；
* 封面链改成「按匹配分遍历全部候选的 coverUrl」，修掉「只问第一首」。

### 3.1 头像链（含三条硬规则）

1. **精确名匹配是默认**：`art_norm_name` 归一化（去空白/小写/全角折半角/拉丁重音折叠）后必须**完全相等**。
   实测宽松匹配 6 例里错 4 例：dizzylab「炒饭」→「铁棍山药炒饭」、「MhT」→「MHTWSNBB666」、
   「洛天依」→「超绝可爱洛天依」、QQ「Khrisma」→「Kharisma」。宽松匹配只在 `allowFuzzy=true` 时开，默认关。
2. **主艺人回退**（`splitPrimary`，默认开）：`"A, B feat. C"` 这种多艺人串在任何源都不存在，
   取第一段（`art_primary_artist`，`/` 切分要求 ≥3 字以保护 AC/DC，括号不配平则放弃）再跑同一条链；
   命中即记 `src=… <-主艺人 X`，并在 `<fnv>.src` 写 `primary=X` 可核对。**不是张冠李戴 —— 取的是这首歌的主艺人**。
3. **取不到就留空**：全链失败返回空，绝不返回专辑封面（用户 2026-10-25 钦定）。

### 3.2 缓存（沿用封面缓存那套「正 + 负」）

```
<exe>\artistimg\<fnv16>.jpg    正缓存（命中即返回，零网络）
<exe>\artistimg\<fnv16>.src    溯源：source / url / bytes / ts / name / primary
<exe>\artistimg\<fnv16>.none   负缓存（文本）：ts + 逐源 "src=<id> kind=miss|fail reason=…"
```
* TTL 7 天（沿用 `kArtistImgNegSec`）；旧的空 `.none` 文件 ts=0 ⟹ 立即重试（升级后自动补图）；
* **`kind=miss`（服务器明确没有）才跳过该源；`kind=fail`（超时/断网/5xx/429）只记原因、下次仍重试**；
* 全部源都是瞬态失败时**不写 `.none`**（避免一次离线把全部艺人钉死成「没有头像」）。

## 4. 实测（真实库 `D:\RTA-hqplayer\MUSIC`，656 首 / 178 专辑）

### 4.1 头像命中：改前 / 改后

判据 = 真的拿到 ≥1 KB 的图片字节（不看任何自述字段）。三个口径分别跑同一份名单：

| 名单 | 口径 | 命中 | 留空 | 命中率 |
|---|---|---|---|---|
| **245 位曲目艺人** | **改前**（1.5.7 原样：网易 list=1、不校验名字） | 148 | 97 | 60.4% |
| 245 | 单源网易 + 精确名（「只接一个源」的上限） | 117 | 128 | 47.8% |
| 245 | **改后**（全信源 + 精确名 + 主艺人回退） | **204** | **41** | **83.3%** |
| **127 位专辑艺人**（艺术家页真实列表） | **改前** | 92 | 35 | 72.4% |
| 127 | 单源网易 + 精确名 | 77 | 50 | 60.6% |
| 127 | **改后** | **117** | **10** | **92.1%** |

* 改前 148 里有 **31 位过不了精确名校验**（粉丝号「周杰伦.」、同名他人、繁简/音标/拼写差异）——
  其中至少一部分贴的是别人的脸，这也是老链路「看起来命中率高但头像经常不是本人」的来源。
  按「名字对得上」的严格口径，改前是 117，改后 204 ⟹ **+87 位（+74%）**，留空 128 → 41。
* 交叉验证：`dist\RLPlayer-1.5.7-win64\artistimg` 里是老链路的真实产物 **93 jpg / 34 none**
  （127 位专辑艺人），与本次「改前 92/127」一致（差 1 位来自当时名单时刻）。
* 用户看到的「246 位里 145 位只剩首字母」= 老缓存只有 93 张，其余全空。

改后每张脸的来源（207 个 `.src` 统计）：**QQ 119 / dizzylab 61 / 网易云 27**，其中 59 张走主艺人回退，
平均 163 KB，合计 34 MB。**只接网易云时它只贡献 27/207 = 13%**。

### 4.3 负缓存：第 2、3 次零网络

同一未命中艺人 `Cirnoice (Remixed by Khrisma)`，删掉它的 `.none` 后连打三次 `POST /api/artist/prefetch`：

```

```

## 5. 边界与未验证（铁律 4）

1. **封面「记录完整就 skipped」仍在**：`enrich_track` 的 step 1 早退没有改 —— 已经 title+artist 齐全的记录
   不会为了补封面重新联网搜索（那会在每次播放时发请求）。用户可见的专辑页封面走的是
   `/api/lib/cover` 链（负缓存 7 天 + `all=1` 强制重试），与本函数的 skipped 语义互不影响。
   本轮只修了「同一次补全里只问第一首」这条。
2. **繁简不折叠**：`倉木麻衣`(标签) 与 `仓木麻衣`(QQ) 只差繁简时仍判为不同名 ⟹ 留空。没有做繁简转换
   （会引入新的误配风险），如实记录。
3. **Discogs 覆盖率依赖限频**：匿名 25/min，全库 245 位跑一轮必有 429；本轮实测 27 个 `fail` 是 429 冷却，
   冷却到期后会重试（`kind=fail` 不参与跳过）。Discogs 对本库（同人为主）贡献为 0 张，符合预期。
4. **头像默认预热名单 = 专辑艺人（127）**，艺术家页渲染的也是这 127 位（`ui_script.h` 从 `/api/lib/albums`
   的 `a.artist` 去重）⟹ 两侧口径一致；本轮为了让数字覆盖更广，额外按**曲目艺人 245** 跑了一遍。
5. **未验证**：真机界面观感（头像是否好看/是否有人脸）需要用户本人看；本轮只验证「取到的是同名艺人的图」。
