# 闭环回传接线纪要（Round 21）

代码：[src/net/rtanet_status.h](src/net/rtanet_status.h)　测试：[tests/test_status.cpp](tests/test_status.cpp)

## 1. 协议扩展（复用 Round 12 的同一条控制面 TCP 连接）

```
S->C  STATUS ts=123456 buf=198.4 drift=+12.7

  ts    端点刚交付的最后一个样本的流内绝对样本号
  buf   端点缓冲水位（毫秒）
  drift 端点估计的相对漂移（ppm，Round 14 的 DriftEstimator）
```

流开始后端点每约 100 ms 回传一行。发送端读取后喂给 `ClockLoop`（Round 19/20）得到速率修正。

**为什么用行式文本**：与握手风格一致、可 telnet 直接观察、排障方便。二进制在这个量级没有收益。

## 2. 实测（13 套测试全绿）

| 验证项 | 结果 |
|---|---|
| 状态行编解码往返 | ts/buf/drift 精确往返，正负漂移都对 |
| 缺 drift 字段 | 正常解析（用于端点尚未估计出漂移的启动阶段） |
| 非 STATUS 行 | 被正确拒绝 |
| **真实回传序列驱动闭环** | 60 秒后水位 **200.02 ms**（目标 200），稳态修正 **+79.1 ppm**（注入 75 ppm） |
| 端点不提供漂移 | 仅凭水位反馈仍能纠偏（方向正确） |

第 4 项是关键：**用真实的状态行（先 format 再 parse）驱动控制器，60 秒后水位收敛到目标 200 ms 的 0.02 ms 以内**。

> 说明：第 5 项的断言只检查**方向**（修正为负），因为该用例的水位演化模型是简化的，
> 不代表真实收敛精度。真正有效的收敛验证是第 4 项。

## 3. 与仿真验证的区别

Round 19/20 是**纯数值仿真**（直接调 `loop.update`）。本轮补的是**协议接线**：

```
端点测量 ──format_status()──> 控制面 TCP ──parse_status()──> ClockLoop ──> 速率修正
```

整条链路已可用真实字符串跑通。**尚未做**的是把它接进 `rtanet_rx` / `rtaplay` 的实际收发循环
（端点真的去写这些行、发送端真的去读），以及在真实网络上做长时间稳定性测试。
