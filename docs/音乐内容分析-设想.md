## 3. 为什么「拆乐器」是坑

1. **源分离**（人声/鼓/贝斯/其他）——2026 年 SOTA 是 **BS-RoFormer / Mel-Band RoFormer**，
   质量优于 Demucs v4；但 Demucs 最好装、Windows 最省事。
2. **逐轨乐器识别**——把分离出来的 stem 送进 AudioSet / 乐器分类模型。天然不准：
   - 长笛 vs 合成 lead、Pad vs 弦乐铺底、军鼓 vs 拍手，模型经常分不清；
   - 一首歌里只出现 3 秒的乐器往往测不出来。
3. **现实产出**是「以钢琴 + 弦乐 + 女声为主，含电子鼓组与合成贝斯」这种描述 + 乐器出现时间轴，
   **做不到「列出全部配器」**。任何看到这种承诺都应警惕。

### 3.1 算力红线（必须先算清）

| 路线 | 可行性 | 代价 |
|---|---|---|
| **CPU（Demucs）** | 可用 | 一首 **5~15 分钟**；曲库 639 首 ≈ 数十小时，**不现实** |
| **GPU** | ❌ 当前不可用 | torch 只为 CUDA 出官方 Windows 轮子；**AMD gfx1201 没有对应 build** |
| **torch-directml** | ⚠️ 未验证 | Windows 上唯一现实的 AMD 路径，但部分算子会退化，需实测 |
| **ONNX Runtime（CPU）** | ✅ 现成 | 适合跑风格标签模型（Jamendo / Discogs-EffNet 导 onnx），比 torch 快得多 |

> ⟹ **结论：先把「不分离」的那部分做扎实（节拍/调性/风格/能量画像），
> 等到确实需要乐器级信息、并且实测出 Demucs 在本机 CPU 或 DirectML 上的真实耗时后，再谈分轨。**

## 6. 若将来实施，验收判据（沿用铁律 3：判据必须真的能证明想证明的事）

1. **BPM**：与人工标注对比，允许 ±2 BPM 或 ×2 / ÷2 的倍频歧义要**显式标注**，不能悄悄猜一个。
2. **调性**：给出置信度；r < 0.5 时 UI 显示「不确定」而不是硬给一个调名。
3. **风格**：Top-5 里必须能人工核对命中至少 1 个；**只给概率不给确定性结论**。
4. **乐器**：必须标注「估计」；**不允许**把分离出的 stem 当作「这首歌有这把乐器」的证据。
5. 任何结果都要能**离线复算**（同一文件同一参数 → 同一结果），否则无法回归。
