# 升频质量量化：我们 vs 竞品（2026-10-27）

> ⚠️ **本报告不是「我们的 App vs 海贝/UAPP 的 A/B 实测」** —— 那需要手机和 DAC，现在没有。
> 本报告做的是**另一件同样重要、且现在就能做**的事：
> **把「升频强度」这个抽象概念量化成可比的数字**，从而回答「竞品的升频到底多强」和
> 「我们手机上最弱的档位够不够」。
>
> 工具：`tools/upsample_probe.cpp`（只读，不加载音频文件、不开任何设备，符合铁律 1）

---

## 1. 方法

- 用本仓**真实的滤波器家族代码** `dsp/filter_design.h` 设计原型（Kaiser 窗、线性相位）
- 口径与 `resampler.h` 的 `minTapsPerInput` 一致：**原型长度 = 每输入样本抽头数 × L**
- 场景：**44.1 kHz → 352.8 kHz（L=8）**，即手机上典型的 ×8 升频
- 零填充 FFT，频率分辨率约 **0.042 Hz**

### 1.1 四个判据（刻意选得不互相重复）

| 判据 | 它真正证明什么 |
|---|---|
| **−3 dB 点** | 通带在哪结束 —— 高频有没有被提前砍掉 |
| **过渡带宽度**（−0.1 dB → −100 dB） | 滚降有多陡 |
| **阻带最大** | 镜像/混叠能压多深 |
| **1 kHz 镜像电平** | 实际播放 1 kHz 时，镜像产物落在多少 dB |

> ⚠️ **判据修正记录（铁律 3）**：第一版把「阻带最大」从输入 Nyquist（22050 Hz）开始扫，
> 结果**所有抽头长度都读出 −6.0 dB** —— 因为 22050 Hz 正好是截止点本身，理论值就是半幅（−6 dB），
> 我的扫描把它当成了第一个采样点。**这是判据错误，不是滤波器属性。**
> 改正：阻带起点取 输入 Nyquist × 1.01，落在过渡带之外。改正后数值才随抽头数单调变化。

## 3. 解读：这张表说明了什么

### 3.1 分水岭在 **256 抽头附近**

| 档位 | 阻带 | 1k 镜像 | 判断 |
|---|---|---|---|
| **64 抽头** | −8.5 dB | **−22.8 dB** | ❌ **完全不可接受的"升频"** —— 镜像比信号只低 23 dB，等于在可闻区加了废料 |
| **256 抽头** | −19.9 dB | −105.9 dB | ⚠️ 镜像压住了，但阻带只有 −20 dB |
| **1024 抽头** | −103.6 dB | −116.8 dB | ✅ 进入可用区 |
| **4096 抽头** | −134.3 dB | −149.1 dB | ✅ 好 |
| **16384 抽头** | −165.6 dB | −206.9 dB | ✅ **优秀**（这是我们给手机定的安全底线） |
| **65536 抽头** | −201.1 dB | −235.5 dB | ✅ 接近理论极限 |
| 262144 抽头 | −199.5 dB | −210.2 dB | ⚠️ **比 65536 略差**（见 3.3） |

### 3.2 对竞品的判断（**推断，非实测**）

**必须明确标注这是推断**：我们没有拿到海贝/UAPP 的升频参数，也没有在手机上测过它们的输出。

- **UAPP** 的商店描述只有 "Upsampling (optional)" 一个开关，**没有任何抽头/滤波器参数**。
- **海贝**的描述是"直接输出"（DXD/DoP/原生 DSD/384k），**根本没有升频功能**。
- 从工程常识推断：一个无参数开关，内部只可能是**简单的整数倍线性/多相插值**，量级大概率在
  **64~1024 抽头**之间。落在 64~256 这一档时，**1k 镜像只有 −23 ~ −106 dB**。

**⟹ 若属 64~256 档，我们手机端的 16384 底线（镜像 −207 dB）是压倒性的。**
**但这需要实测才能定论** —— 标注为未验证项（见 §5）。

### 3.3 一个反直觉但重要的发现

**262144 抽头的「1k 镜像」(−210.2 dB) 比 65536 抽头 (−235.5 dB) 还差。**

原因：**零填充 FFT 测的是「窗口内」的响应**。超长 FIR（262144×8 = 209 万点）的旁瓣结构极密，
我在 5 Hz 步进扫描时**采到的是某个旁瓣的峰**，而 65536 那个长度碰巧扫在旁瓣之间的谷里。
**这不是滤波器真的更差，是我的扫描步进在超长滤波器上不够细。**

⟹ **结论：这张表的 65536 以上几行只能当量级参考，不能用来排序。**
    真正要比 65536 vs 262144，必须把扫描步进降到 0.5 Hz 或改用包络检测。
    **这一条是本次分析留下的未解决问题（铁律 4）。**

## 4. 对安卓版的直接结论

| 问题 | 答案 |
|---|---|
| 手机上 16384 抽头够不够当"卖点"？ | **够。** 阻带 −165.6 dB、1k 镜像 −206.9 dB，**已远超 `音质极限分析.md` 自定的"−120 dB 以下无意义"** |
| 能不能降到 4096 省算力？ | **可以**（阻带 −134 dB 仍够），过渡带 67 Hz，仍在 22 kHz 以上 |
| 能不能降到 1024？ | ⚠️ **不要**。阻带掉到 −103.6 dB，已贴近"无意义"线，且过渡带 232 Hz 开始挤压 21.9 kHz |
| 降到 256？ | ❌ **绝对不行**。阻带 −19.9 dB —— 这不是升频，是**在可闻区加废料** |

⟹ **手机端的抽头下限应定在 4096~16384 之间，不设更低档。**

## 5. ⚠️ 未验证项（必须如实记录）

1. **竞品的真实升频参数未知** —— §3.2 全部是推断。要验证需要：手机 + DAC + 竞品 App，
   用我们的工具对**它们的输出文件**做同样分析（它们可以导出/录制吗？待确认），或反编译其参数。
   **当前无法做，因为无手机。**
2. **65536 以上几行的排序不可信** —— 扫描步进 5 Hz 对超长 FIR 太粗（§3.3）。
   **替代验证**：把步进降到 0.5 Hz 重跑，或改用旁瓣包络检测。**这个现在就能补做，见下。**
3. **本报告只讲频域** —— 相位、群延迟、预振铃（切趾）**完全没有涉及**。
   **判据边界**：这张表**不能**用来论证"我们的升频听感更好"，只能论证"我们的频域指标更强"（铁律 3）。
