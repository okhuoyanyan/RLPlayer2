## 2. 诊断

### 2.1 HF-01：1.log 的 UNSUPPORTED_FORMAT 是格式协商失败

代码链路 tools/rtaweb.cpp:967：

    const auto rates = WasapiOutput::exclusive_rates(p.device, bits, in.channels);
    bool ok = rates.empty();
    for (auto r : rates) if (r == deviceRate) ok = true;

rates.empty() 被当成未知先试。如果设备在独占模式下不接受 24-bit，IsFormatSupported 对所有候选率都返回非 S_OK，列表为空，代码继续用 24-bit Initialize，于是报 UNSUPPORTED_FORMAT。

tools/rtaweb.cpp:853：

    cfg.outBits = (p.bits > 0) ? p.bits : 24;

UI 的 0 选项标签就是 24 bit（不是跟随源）。16-bit FLAC + 只支持 16-bit 的板载 HD Audio 会直接撞上。

另一条并行嫌疑：保存的 device endpoint 已失效或被切换。exclusive_rates 找不到 endpoint 时返回空，open 用旧 id 打开，格式检查与实际端点不一致。日志里只有友好名，没有 endpoint id，无法区分。

结论：不是 DSP、不是抖动、不是 DSD 调制器、不是 GPU。高概率是 24-bit 不被该设备独占模式接受 + 空列表被当成功；中概率是端点失效。前一条 44.1k/24 能播 83 秒说明不能简单断言设备完全不支持 44.1/24，必须把设备当前状态/端点与格式协商一起修。

### 2.2 HF-03：2.log 的 vector too long 发生在 PLAY 之前

PLAY 日志是在 read_any()、ISP 扫描、管线配置、信号链 JSON 之后才写的。4 条 vector too long 没有 PLAY，说明失败点在：

1. read_any()：.flac -> read_via_ffmpeg() -> ffmpeg 写临时 WAV -> read_wav()；或 read_dsd()。
2. detect_isp 的 planes 分配（rtaweb.cpp:895）。
3. 管线建立/滤波器设计阶段（cfg、Pipeline、resampler 构造）。

vector too long 是 std::length_error，常见于负数或溢出被当成巨大 size_t，不是文件真的太大。重点检查：

- src/audio/wav.h:97-99：bytesPer = bps/8；nSamples = dataLen/bytesPer；raw.resize(nSamples)。临时 WAV 的 fmt 头异常（bps 非 8/16/24/32、ch 异常、data size 异常、截断）时没有校验；bps<8 还会除零。
- tools/rtaweb.cpp:895：planes.resize(channels, vector<double>(in.frames()))；如果 read_any 返回异常 channels/frames，会分配巨大二维 vector。
- src/dsp/resampler.h:62-64：L/M 由 gcd 计算；如果某条路径把 outRate/inRate 传成 0，M 可能为 0，maxOutFrames 算出 inf，转 size_t 后可能触发 vector too long。

当前不能只凭日志断定是哪一处。热修复应先做两件事：
1. 加固并明确报错：read_wav 校验头字段；read_any 包一层，把文件、阶段、临时 WAV 路径/大小写进错误；resampler 对 M==0 或非有限值直接拒绝。
2. 补日志：START file=...（read_any 之前）、DECODE rate/ch/bits/frames/tempWav/size（read_any 之后）、END file=...。

### 2.3 HF-04：设备不支持 0 Hz 与 1.0.4 的保护矛盾

错误来自 tools/rtaweb.cpp:977，条件是 deviceRate==0。1.0.4 在 tools/rtaweb.cpp:841 已有：

    if (in.rate == 0 || in.frames() == 0) {
        ps.error = 解码结果为空 ...; return false;
    }

如果 2.log 确实来自 1.0.4，那么 in.rate 不是 0、deviceRate 却为 0，只剩 DSD 路径或另一条代码路径；否则就是旧版/开发构建/多个实例写同一个日志。

先确认：2.log 对应 rtaweb.exe 的 SHA256/文件版本、包名、launcher.log 是否同时起过两个实例。仅凭日志不能把这条算成 1.0.4 的确定 bug。

### 2.4 HF-05：END pos=0 error=空

PLAY 后约 4 秒 END，pos=0、total 正常、error 为空。最可能是用户没听到声音后手动停止/切歌，不是崩溃。需要 STAT 的 w0/pad 判断是没喂进去还是设备没开；本轮热修复不建议改。

## 3. 派单建议

### HF-01 [P0] WASAPI 格式协商与位深/采样率回退

目标：1.log 的 44.1k/16-bit 源在只支持 16-bit 的独占设备上也能播；不能播时给出可操作信息，而不是 UNSUPPORTED_FORMAT。

改动点：
- src/audio/wasapi_out.h：增加格式探测返回 {rate,bits} 列表；open() 失败时返回结构化原因（请求格式、设备支持列表、HRESULT）。
- tools/rtaweb.cpp：rates.empty() 不能当成功；依次尝试 24-bit -> 16-bit -> 32-bit（或按源位深优先），真正 Initialize 成功后才使用；把最终生效 outRate/outBits 写进信号链/PLAY 日志。
- 端点校验：open() 前 GetState；失效则回退默认端点，并在日志写 device id。
- UI 不新增开关；默认行为是能播就播，不能播说清楚。

验收：
1. 16-bit 源 + 16-bit-only 设备：能播，实际 outBits=16；不出现 UNSUPPORTED_FORMAT。
2. 24-bit 设备：仍按 24-bit，不降级（回归）。
3. 设备完全不支持请求的 rate/bits：错误里带 device id、请求值、实际支持列表。
4. 1.log 场景复现通过；截图不再出现该错误。

风险：自动降位深会改变输出格式，需要在信号链和 UI 明示实际 16-bit，不能悄悄变。

### HF-02 [P1] 端点状态与同设备前一条能播、后一条失败

目标：区分格式不支持与保存的 endpoint 失效或被切换。
改动点：PLAY/END 日志增加 deviceId；open 找不到 endpoint 时明确报端点不存在/已禁用，并尝试默认端点；处理 AUDCLNT_E_DEVICE_INVALIDATED。
验收：1.log 的第二条流要么正常播放，要么错误明确是 endpoint 失效，不再是笼统 UNSUPPORTED_FORMAT。

### HF-03 [P0] vector too long 加固、定位与可观测性

目标：不再出现不可定位的异常 vector too long；即使源文件/临时 WAV 异常，也要给出文件、阶段、头字段。

改动点：
- src/audio/wav.h::read_wav：校验 channels 1..32、bits 8/16/24/32、bytesPer>0；校验 dataLen/nSamples 上限与 dataPtr+dataLen 边界；失败错误包含文件路径、fmt 头字段、data size、临时 WAV 路径/大小。
- src/audio/audio_loader.h：ffmpeg 退出后检查临时 WAV 大小/头；把临时 WAV 路径/大小带进异常。
- tools/rtaweb.cpp：read_any 外层捕获 length_error/bad_alloc，错误写成阶段=解码/临时WAV/文件=...，不要只留 what()；detect_isp 前检查 channels/frames 合理性；resampler 构造前检查 inRate/outRate>0、taps 范围，M==0 直接报错。
- 日志：START（read_any 前）、DECODE（read_any 后）、END file=...。

验收：
1. 用 2.log 的失败文件（或最小复现文件）在 backend=null 下：要么正常播放，要么错误明确到阶段/文件/头字段；不再出现裸 vector too long。
2. 构造异常 WAV（ch=0/65535、bps=0/7/33、dataLen 超大、截断）单元测试，全部抛具体错误，不崩溃、不巨大分配。
3. resampler 收到 inRate=0/M==0 时直接报错，不进入 maxOutFrames。
4. 正常 FLAC/DSF 回归：ctest 29/29，DSD 通路 THD+N 不退化。

风险：校验过严可能误杀合法但少见的 WAV（如 8-bit、32-bit float）。要按 WAV 规范放行，只拒绝明显非法/越界值。

### HF-04 [P1] deviceRate==0 防御与版本核对

改动点：
- play_one 在能力检查前增加 deviceRate==0 保护，错误写 inRate/frames/rate/dsd。
- PLAY/END 日志带 rtaweb 版本和文件；启动时写一次版本。
- 先核对 2.log 对应 rtaweb.exe 的 SHA256/文件版本；如果与 1.0.4 包不一致，本条转为旧构建/多实例排查，不混入热修复。
验收：不会再出现无上下文的设备不支持 0 Hz 错误；日志能看出 inRate/frames/rate/dsd。

## 6. 明确不要做

- 不要把 exclusive_rates() 的空列表继续当成功。
- 不要用 catch(...) 吞掉 vector too long 然后继续播放；必须带文件/阶段报错。
- 不要为了绕过 1.log 强制所有设备 16-bit；支持 24-bit 的设备必须保持 24-bit。
- 不要在本轮改 LNS15/DSD 调制器/滤波器/NAA；这些与两份日志无关。
- 不要在未确认二进制版本前，把 2.log 的 0 Hz 当成 1.0.4 的确定 bug 修。
