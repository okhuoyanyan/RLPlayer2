# 端点实时节奏与闭环验证纪要（Round 24）

代码：[tools/rtanet_rx.cpp](tools/rtanet_rx.cpp)

## 1. 本轮做了什么

给文件 sink 加了 `--realtime`：让已消费帧数按墙钟推进，而不是瞬时吃光所有数据。
并修正计时起点——**必须从收到第一个包开始算**，而不是进程启动
（否则端点等发送端连接的那几秒会被算成已放行，开场就一次性追赶一大段）。

## 2. 结果：仍然没能验证闭环，根因已定位到架构层

实测（8 秒 / 44.1k / 24bit，72 条状态回传）：

```
闭环: 收到 72 条状态回传 | 末次水位 0.0 ms | 末次漂移 -0.0 ppm | 最终修正 +159.8 ppm
逐位比对: 逐位完全相同 (2116800 字节)
```

水位读数依然是 0.0 ms，外环依然把修正推到 +159.8 ppm。

### 根因

接收循环是单线程：

```cpp
while (true) {
    recv_from(...)                     // 收包，累加 framesIn
    while (jb.pop(...)) deliver(...)   // deliver 里带实时节奏，会 sleep
}
```

deliver 阻塞时，循环停在里面收不了新包，framesIn 停在原地不涨；
而 framesOut 被时钟放行继续涨，二者始终贴合，**水位恒为 0**。

也就是说：包的积压其实发生在 UDP 接收缓冲里，而 framesIn 根本没统计到那部分。
**水位这个指标本身测错了。**

## 3. 正确的修法（下一步）

必须把接收与交付解耦：

1. **独立播放线程**：接收线程只管收包入抖动缓冲；播放线程按 DAC 时钟取数据。
   这是所有真实播放器的标准架构。
2. **非阻塞播放门**：接收循环照常收包；交付时若时钟未放行就跳出（不 sleep 在里面），
   下一轮再试。需要给抖动缓冲加 peek()。

推荐第 1 种——它同时也是接真实 WASAPI 输出时必须的结构。

## 4. 可确认与不可确认

**可以确认**：
- 状态回传协议正常（72 条 / 8 秒，约每 111 ms）
- 漂移估计准确（回环上正确报 -0.0 ppm）
- 逐位完美性未被任何改动破坏（始终 2116800 字节逐位相同）

**不能确认**：
- 闭环外环在真实路径下的行为 —— 水位指标测错了，测不出真实积压

> 已连续两轮卡在同一处。根因不在控制器，而在端点的单线程结构。
> 在把接收/交付解耦之前，任何闭环已验证的结论都不成立。
