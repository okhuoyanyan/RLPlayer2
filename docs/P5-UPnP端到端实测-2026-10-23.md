# P5 UPnP 投放端到端实测纪要（2026-10-23，第一次真机）

> 用户授权设备：**192.168.50.109**（`N1000_UPNP`，upmpdcli 1.4.12 + MPD 0.22.0 + MiniDLNA 1.2.1）。
> 结论：**控制面全部正确，供源侧被网络环境阻断**。以下是逐层证据。

## 1. 设备识别（SSDP 被拦，直连描述成功）

- `upnp_scan.exe` / 手写 M-SEARCH：**发现 0 个设备** —— 本机网络中 SSDP 组播（239.255.255.250:1900）无任何响应
  （路由器 IGMP snooping 或防火墙拦截，非程序问题；同机 ping 设备 0 ms）。
- `rtacast --dev http://192.168.50.109:49152/` **直连描述成功**：
  - friendlyName：`N1000_UPNP`
  - modelDescription：`UPnP front-end to MPD`（upmpdcli 1.4.12 / libupnpp 0.19.2）
  - AVTransport 控制端点：`/uuid-f4fedde9-.../ctl-urn-schemas-upnp-org-service-AVTransport-1`
  - 另外 8200 是 MiniDLNA 状态页（音频 0 个文件，非播放源）。

## 2. 控制面（SOAP）全部正确 ✅

用 Postman 式手工 SOAP 与 `rtacast` 两条路径都验证：
- `SetAVTransportURI`(带完整 DIDL-Lite + protocolInfo) → **HTTP 200 OK**；
- `Play` → 200 OK，`GetTransportInfo` 返回 `PLAYING`；
- `GetMediaInfo` / `GetPositionInfo` 可解析（`CurrentURI` 只在 MPD 真正起播后才回填，这是 upmpdcli 的行为，不是缺陷）；
- 错误码解析、DIDL 转义、UPnPError 结构化——均按契约工作。

## 3. 供源侧（关键失败点）❌ 环境问题

MPD 侧日志（直连 6600 查询 `status`）给出**决定性证据**：

```
error: Failed to decode http://192.168.50.140:8912/stream/<hash>.wav;
       CURL failed: Connection timed out after 10010 milliseconds
```

排查过程（逐步排除）：
1. 本机 `rtacast` 的 `UpnpHttpServer` **确实绑定 `0.0.0.0:8912`**（`Get-NetTCPConnection` 可证）；
2. **本机自测通过**：`http://192.168.50.140:8912/...` 与 `127.0.0.1` 均 200；
3. 换成**最简 Python `http.server`** 做对照（排除我们代码的因素）：本机访问 200，
   设备侧 MPD 仍 `Failed to decode ... Connection timed out`；
4. **加防火墙放行**（先按端口 8912、再按程序 python.exe，覆盖 Domain/Private/Public 全 profile）：
   设备仍超时；
5. **反向证据**：`Get-NetTCPConnection -RemoteAddress 192.168.50.109` 只看到**我主动连它的 6600**，
   **从未出现设备连入本机 8912/8913 的连接**。

**因此判定：设备与开发机之间，TCP 入站方向被阻断**（路由器 AP 隔离 / 客户端隔离，或设备侧策略），
不是 RLPlayer 的代码缺陷。icmp ping 通但 TCP 入站不通，是典型的 AP/客户端隔离特征。

## 4. 待用户侧确认/处理（这样打一枪就能进下一步）

任选其一即可让 P5 端到端跑通：
1. 在路由器关闭 **AP 隔离 / 客户端隔离**（或把 .109 与本机放到同一非隔离 VLAN）；
2. 让设备访问一个**公网可达**的地址（我可以起临时隧道），证明设备出网正常、只是不进内网；
3. 或者把设备换到与本机同一交换机/无隔离的 SSID（2.4G 访客网络通常隔离）。

## 5. 代码侧结论（本轮不需要改代码）

- `rtacast` 的 SOAP/DIDL/Range/供源实现**经受住了真机验证**（200 OK、PLAYING、错误码结构化）；
- 唯一可优化点：**SSDP 组播失败时应提示"可改用 --dev http://IP:PORT 直连描述"**（已支持但提示不够显眼），
  以及 `rtacast` 在 `--list` 空时应打印可能原因（当前已有"组播被防火墙或代理拦截"提示，可再补直连用法示例）。
