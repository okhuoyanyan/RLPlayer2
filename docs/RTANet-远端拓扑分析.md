# 远端路径拓扑分析：常规远端播放 vs 远端升频回传（2026-10-27）

> 起因：用户提出「RTANet 在手机上的用法」时指出 —— **本来说的是远端播放，被拓展成了远端升频回传**。
> 问：可行性多高？延迟、时钟影响多大？
> 本文只做**判断与依据**，不改代码、不立项。结论档：`docs\安卓版-开发结论.md`

---

## 0. 结论先行（三句话）

1. **常规远端播放（DSP 全在发送端，端点只搬运）= 已经做过的路径，风险极低**；
   但它**救不了手机** —— 因为升频没在手机上跑，手机只是根「昂贵的线」。
2. **远端升频回传（升频在手机 GPU 跑，结果回传给 PC 端 DAC）= 技术可行、生态可行，
   但有一个尖锐的时钟矛盾：用异步 SRC 补偿漂移，就破坏了「逐位等价」；用整数倍率，就必须做时钟主从。**
3. **真正值得做的是形态 C：升频在手机、DAC 也插在手机上（UAC2 直连）** ——
   这样手机是**唯一的时钟主**，没有跨机漂移，RTANet 只负责**控制面/遥控**。**这是矛盾最少、卖点最强的组合。**

---

## 1. 先把两种拓扑摆清楚

### 形态 A：常规远端播放（DSP 在发送端，端点只搬运）

```
PC（解码 + 升频 + 卷积 + PEQ）── RTANet ──> 手机/端点（receive → buffer → 送 DAC）
                                              ↑ 时钟主在这里
```

- **这就是 RTANet 当初的设计形态**，`rtaplay --net` + `rtanet_rx.exe` 已验证**逐位一致**
  （`docs\RTANet-冻结说明.md:26`，`verify.ps1` 第 10 项 DirectSDM 端到端）。
- 升频在 PC 上完成，手机侧零 DSP。
- **对手机的算力要求 = 0** —— 但**对手机的产品意义也 = 0**（用户手里的手机变成一根线）。

### 形态 B：远端升频回传（升频在手机 GPU，结果回传给 PC 的 DAC）★ 用户问的这个

```
PC（解码，送 PCM）── RTANet ──> 手机（GPU 升频 ×16）── RTANet ──> PC（送 DAC）──> DAC
                                                                   ↑ 时钟主在这里
```

- **可行性：技术上高**。协议是双向的，流水线都能跑。
- **但**：为了一次播放，数据在网络上来回两趟，**延迟翻倍**；
  更关键的是 **DAC 的时钟在 PC 端，而升频在手机端** —— 两台机器的晶振漂移**直接落在输出通路上**。

### 形态 C：手机一体（升频 + DAC 都在手机）★ 我判断的最优解

```
PC（曲库 / 控制面 / 元数据）── RTANet（控制/遥控）──> 手机（解码 + GPU 升频 + UAC2）──> DAC
                                                        ↑ 唯一时钟主 = DAC
```

- **没有跨机音频流**，因此**没有漂移问题**（`clock_loop.h` 那套 PI 控制器根本用不上）。
- RTANet 退化为**控制面与曲库同步**（这正是它「轻量、可控」的优势所在）。
- **卖点**：手机上跑我们自己的 GPU 升频 + UAC2 bit-perfect 直连 —— 这是**别人做不到**的组合。

---

## 2. 延迟：三种形态差别巨大

| 形态 | 端到端延迟构成 | 典型量级 | 对听音的意义 |
|---|---|---|---|
| **A 常规远端** | 网络抖动缓冲（`targetBufferMs` **默认 200 ms**）+ 端点缓冲 | **200~350 ms** | 纯听音无感；**看视频/打游戏必然不同步** |
| **B 升频回传** | A 的全部 + **回传方向再一次抖动缓冲** + 手机→PC 网络 | **400~700 ms** | 同上，且更差 |
| **C 手机一体** | UAC2 等时缓冲（几十 ms）+ DSP 分块 | **20~60 ms** | 接近本地播放器水平 |

**关键数据**：`src\net\clock_loop.h:19` 的 `targetBufferMs = 200.0` 是**默认目标水位**。
这套设计是**为听音优化的**（缓冲浅 = 抵抖动能力弱），不是为交互延迟优化的。

### 2.1 延迟不影响音质，但影响**时钟矛盾的规模**

延迟本身**不劣化音质**（只要缓冲不欠载/不溢出）。但它决定了两件事：

1. **漂移累积的时间窗口**：缓冲越深，能容忍的漂移越大（200 ms 缓冲可以容忍晶振差 200 ppm 跑 1000 秒）。
2. **纠偏的响应速度**：`slewPpmPerSec = 20.0`（变化率上限）意味着**修正必须以 ppm 级缓慢施加**，
   否则会变成可闻的音高抖动。

---

## 3. 时钟：这才是真正的问题所在

### 3.1 漂移的物理量级（这是可控的）

`docs\时钟漂移纪要.md:7` 已写明：**10 ppm 差，1 小时累积 36 ms**。
消费级晶振典型 ±20~50 ppm（温漂后），**完全在 500 ppm 修正上限内**。

⇒ **「缓冲会不会溢出/耗尽」这个问题，技术上已经解决了** —— 闭环 + 0.5 ppm 估计精度（`时钟漂移纪要.md:32-35`）。

### 3.2 但是：现有闭环的实现方式与「逐位等价」直接冲突

**这是本次分析最尖锐的发现。**

`src\net\clock_loop.h:10-11` 写得很明确：

> 补偿执行方式（发送端）：按修正后的比率做**异步重采样**。本文件只负责算出修正量，
> 具体施加由发送端的重采样器完成（**音质影响最小；丢/插样本的做法不采用**）。

而 `tools\rtaplay.cpp:1200` 的实际实现是：

```cpp
const double audioSec = (double)sent / ((double)nf.rate * (1.0 + applied * 1e-6));
```

⇒ **「按修正后的比率发送」= 发送端和端点之间实际上发生了异步重采样。**

| 问题 | 后果 |
|---|---|
| 异步 SRC 是一次**有理倍率重采样** | 输出**不可能再与源逐位一致** —— 每个样本都被重新算过 |
| 当 `applied == 0`（无漂移）时 | 退化为「按实时节奏发送」，整数样本搬运，**可以逐位** |
| 当 `applied != 0` | **必然破坏 bit-perfect** |

**这就是 RTANet 与「逐位等价」的根本矛盾**：它为了对齐时钟，牺牲了逐位性。

> ⚠️ 注意：`verify.ps1` 第 10 项能验证「逐位一致」，是因为那是**离线、不实时、无漂移补偿**的场景。
> **实时播放且闭环生效时，逐位性是不成立的** —— 这一点必须写进结论档，不能含糊。

### 3.3 要同时保住 bit-perfect 和时钟，只有两条路

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **B1. 时钟主从（推荐）** | **让 DAC 侧成为唯一时钟主**：PC 侧按 DAC 的实际消费速率**整数样本搬运**，缓冲靠「整数样本的增减」而不是「重采样」来吸收 | 缓冲抖动会变成**极低频的小台阶**（每 N 秒丢/补一个样本） | 严格意义上也不是 100% bit-perfect（有丢补），但**无重采样**；且丢补频率可算、可监控 |
| **B2. 全链路共时钟** | 让两端用**同一个时钟源**（例如发送端按 DAC 的 feedback 直接产生样本） | 需要**发送端能实时产出**（DSP 必须完全实时稳定） | 最理想，但把「整曲先算完再播」的架构彻底推翻 |
| ~~B3. 异步 SRC~~ | 现状 | 破 bit-perfect | **与用户的精度目标直接冲突，不可用于我们** |

**⇒ 结论：形态 B 要用，就必须把 `clock_loop` 的补偿执行方式从「异步重采样」改成「整数丢补 + 水位控制」**，
并且**把「是否处于 bit-perfect」暴露成可见状态**（现在已经有 `STAT` 的 `bf` 字段可以复用）。

## 4. 三个形态的可行性总评

| | 形态 A 常规远端 | 形态 B 升频回传 | **形态 C 手机一体** |
|---|---|---|---|
| 技术可行性 | ⭐⭐⭐⭐⭐ 已验证 | ⭐⭐⭐ 可行 | ⭐⭐⭐⭐ 需 UAC2（见结论档） |
| 对手机算力的利用 | ❌ 零 | ✅ 用足 GPU | ✅ 用足 GPU |
| 延迟 | 200~350 ms | **400~700 ms** | **20~60 ms** |
| 跨机时钟漂移 | 有（已闭环，但**牺牲 bit-perfect**） | 有（**两次传输，问题加倍**） | **无** |
| 与「逐位等价」相容度 | ⚠️ 闭环生效时**不相容** | ⚠️ 更差 | ✅ **天然相容** |
| 产品卖点 | 弱（手机＝一根线） | **中**（手机当加速器） | **强**（手机＝完整播放器） |

---

## 5. 我的建议

**形态 C 为主线，形态 B 作为可选项，形态 A 保留为既有能力。**

理由：
- **形态 B 的最大代价不是延迟，而是「它让两台机器的时钟问题重新变大，而赢来的只是让 PC 有个 DAC」** ——
  成本与收益不成比例。
- **形态 C 把所有时钟问题消掉**（单机单主），同时**保住了 GPU 升频这个差异化卖点** ——
  这正是用户 2026-10-27 定的方向（`docs\安卓版-开发结论.md`）。
- **RTANet 在形态 C 里的角色是控制面**（遥控、曲库同步、状态回显），
  **这反而是它最合适的角色**：不需要传输音频，就不需要和时钟搏斗，也回避了「生态上没有数播能装」的问题——
  因为**对端是我们自己的手机 App**，不是第三方硬件。**这是它复活的关键。**

### 何时才值得做形态 B

只有当出现这种需求时：**用户想在 PC 的高端 DAC 上听手机端升频的结果**（例如 PC 接了台几万块的解码器）。
那是**小众中的小众**，建议**先不做**，但**架构上留口子**（协议已经具备）。

## 6. 需要用户拍板

1. **RTANet 在手机版里的角色**：形态 C（控制面 + 手机一体化）为主，还是也要做形态 B（远端升频回传）？
2. **若做形态 B**：是否接受把 `clock_loop` 的补偿从「异步重采样」改成「整数丢补」——
   这意味着**丢掉现有的"最小音质影响"设计，换取 bit-perfect 的严格性**？
3. **bit-perfect 的可观测性**：是否同意把「当前是否处于严格 bit-perfect」做成界面可见状态
   （复用现有 `STAT` 的 `bf` 字段），而不是让用户凭猜测？
