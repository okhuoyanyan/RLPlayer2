# RTANet 收发驱动与端到端验证纪要（Round 12）

代码：[src/net/rtanet_stream.h](src/net/rtanet_stream.h)　测试：[tests/test_rtanet_e2e.cpp](tests/test_rtanet_e2e.cpp)

> 全程本机回环（TCP 控制面 + UDP 数据面），不涉及任何音频设备。

## 1. 控制面协议（行式文本，可 telnet 手工调试）

```
C->S  HELLO RTANET/1
S->C  OK RTANET/1 rta-endpoint
C->S  FORMAT rate=48000 bits=24 channels=2
S->C  OK FORMAT                 （不支持则 ERR FORMAT <原因>）
C->S  START stream=7
S->C  OK START port=<UDP 端口>
      ...UDP 数据流...
C->S  STOP / PING / BYE
```

## 2. 端到端实测结果（10 套测试全绿）

条件：48 kHz / 24 bit / 立体声，48000 帧（1 秒），每包 128 帧，共 **375 包**。

| 验证项 | 结果 |
|---|---|
| 控制面握手 | 成功（控制端口 10523 → 端点返回 UDP 端口 54227） |
| 发送帧数 | 48000 帧 ✓ |
| 收到包数 | **375 / 375** ✓ |
| 按时间戳落位 | 48000 帧，**缺帧 0** ✓ |
| **样本一致性** | **不符 0 / 96000 ⟹ 接收端与发送端逐位相同** ✓ |
| 丢包 / 重复 | **0 / 0** ✓ |
| 格式协商 | 协商结果与请求一致 ✓ |

**这是「两机方案」的完整链路演练**：DSP 机 → 控制面协商 → UDP 流 → 端点抖动缓冲 → 按时间戳还原，
全程无任何数值改动。

## 3. 本轮踩的坑

### 坑 1：`run_code` 自身的 120 秒默认超时

我给了 pwsh 工具 900 秒，但 `run_code` 程序本身有 120 秒默认上限（上限 600 秒）——
构建 + 测试一起跑就撞上了。**内层工具的 timeout 不能替代外层程序时限。**

### 坑 2：UDP 接收漏设超时 ⟹ 收不到包就永久阻塞

只设了接收缓冲大小，没设 `SO_RCVTIMEO`。一旦包没到，`recvfrom` 会一直挂着，
测试永远不返回。加上 200 ms 超时后正常。**任何阻塞式网络读取都必须带超时。**

（这两条都是工程纪律问题，不是逻辑缺陷；但都会让 CI/自动化静默挂死。）
