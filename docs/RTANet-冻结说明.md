# RTANet 冻结说明（2026-10-27）

> 用户原话（261027-04 #5）：
> 「RTANet保留，但是暂不启动，主要是几乎没有数播能安装我们的协议，这需要硬件支持，
> 我们暂时没有这个能力影响硬件选择。」

## 结论

**保留代码，冻结启用。** 不做删除、不加界面入口、不对外宣传。

## 它是什么

RTANet = 我们**自研**的 UDP 音频传输协议（DSP 机 → 端点机 → DAC）。

- 代码：`src/net/rtanet.h`（14,353 B）+ `src/net/rtanet_stream.h`（10,547 B）
- 端点程序：`tools/rtanet_rx.exe`（包内 `tools\\rtanet_rx.exe`，397,312 B）
- 命令行入口：`rtaplay.exe --net`

### 设计要点（代码注释里的原始理由）

| 项 | 内容 |
|---|---|
| 为什么不硬啃 NAA | NAA 无公开规范、无源码、无 Wireshark dissector（实测手册 65 页对端口/组播提及 0 次） |
| 为什么自研更好 | 显式**绝对样本号时间戳** + 抖动缓冲 + 序号，可**逐位验证**；NAA 本身不决定音质，端点时钟/供电/缓冲才是瓶颈 |
| 数据面 | UDP，定长 40 字节头 + 打包 PCM（16/24/32 bit 紧凑打包，128 帧/包 < MTU） |
| 音质 | 可做到**逐位一致**（`verify.ps1` 第 10 项 DirectSDM 端到端就是靠它验证的） |

## 与 UPnP/DLNA 的区别

| | **RTANet** | **UPnP/DLNA** |
|---|---|---|
| 本质 | 自研 UDP 协议 | 行业标准（SOAP 控制 + HTTP 传输） |
| 对端要求 | **必须也装 RLPlayer**（`rtanet_rx.exe`） | 任何 UPnP 渲染器（数播/电视/音箱/手机 App） |
| 音质 | 可逐位验证 | 取决于渲染器，可能被重采样（我们会给 Match/Mismatch 取证告警） |
| 延迟 | 低（UDP 直连） | 较高（HTTP + 缓冲） |
| 代码量 | ~24 KB | ~86 KB（`upnp.h` + `upnp_control.h` + `cast_service.h`） |
| 现有入口 | **仅命令行** | 完整界面 |

## 为什么冻结

1. **生态问题，不是技术问题**：几乎没有数播/网桥能安装我们的端点程序。
   要让它有用，需要影响硬件厂商标配我们的协议 —— 这超出我们的能力范围。
2. **对普通用户等于不存在**：GUI 里从来没有入口（`f65440b` / 1.3.16 移除了 NAA 发现与 UI 选项），
   普通用户永远看不到它，留着入口只会造成"这功能能用吗"的困惑。
3. **但删除有代价**：`verify.ps1` 第 10 项（DirectSDM 端到端逐位一致）依赖它；
   两台自家机器之间做 bit-perfect 传输时它仍然是唯一手段。

## 保留的具体形态（当前代码状态，已核实）

- `tools/rtaweb.cpp` **全文零使用** RTANet 符号（第 67 行注释记录了 2026-10-27 删掉那个无谓 include）
- GUI 后端下拉只有：`wasapi` / `wasapi-shared` / `asio` / `upnp` / `null`
- 设置文件里**没有** rtanet 相关开关
- 包里仍带 `tools\\rtanet_rx.exe`（供命令行/排障/回归使用）

## 未来如果重启

触发的条件（任意一条）：
1. 有硬件厂商愿意预装/支持我们的端点程序
2. 我们自己要做"两台 RLPlayer 之间无损直传"的产品形态
3. 需要做比 UPnP 更严格的 bit-perfect 网络传输验证

重启时需要做的（现在没做，因为冻结）：
- 给 GUI 一个后端入口（当前下拉里没有）
- 端点程序的易用性（现在要手动敲 `rtanet_rx.exe`）
- 与现有 UPnP 投放的互斥关系（同时只能选一种输出）
