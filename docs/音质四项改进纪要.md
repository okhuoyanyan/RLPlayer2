## 1. 抖动整形按采样率重标定（这一项之前是【错的】）

### 1.1 问题

旧实现用 NTF(z) = (1 - z^-1)^N 且固定 r=1，与采样率无关：

    |NTF(f)| = (2·sin(πf/fs))^N

- fs = 176.4 kHz：20 kHz 处约 **-28 dB**（温和，没问题）
- fs = 44.1 kHz：20 kHz 处约 **+52 dB** —— 把 15~20 kHz 的白噪放大约 400 倍

也就是说：**只要用户选"保持源采样率 + NS9"，就会在 44.1k 输出时听到一层高频嘶声**，
而当时的测试只测 0~20 kHz 的【总功率】（还是在 176.4k 下测的），根本抓不到。

### 1.2 修法

让零点半径随采样率重标定，使可听带上端的单级增益受控：

    |1 - r·e^(-jw)|^2 = (1-r)^2 + 4r·sin^2(w/2)
    要求 (1-r)^2 + 4r·s2 <= g^2，其中 g = 10^(6dB/(20N))   ← 每级允许增益
    解得 r = [ -(4·s2-2) + sqrt((4·s2-2)^2 - 4(1-g^2)) ] / 2

注意：|1 - r·e^(-jw)| **不等于** 2r·sin(w/2)（那个等式只在 r=1 成立）。
本轮一开始用错这个式子，得出"r 越小高频越干净"的反向结论，实测才发现。

结果：

| 输出采样率 | r | 19 kHz 处 | 20 kHz 处 |
|---|---|---|---|
| 44.1 kHz | 0.083 | +5.7 dB | +6.0 dB |
| 96 kHz | 0.741 | +2.8 dB | +6.0 dB |
| 176.4 kHz | 1.000 | -32.0 dB | -28.2 dB |
| 705.6 kHz | 1.000 | -139.0 dB | -135.0 dB |

### 1.3 实测收益（-60 dBFS 1 kHz 正弦 -> 16 bit，带内 20~20 kHz）

| 采样率 | TPDF | NS9 | NS9 相对 TPDF |
|---|---|---|---|
| 44.1 kHz | -93.7 dB | -97.2 dB | **+3.5 dB** |
| 96 kHz | -97.2 dB | -108.1 dB | **+10.8 dB** |
| 176.4 kHz | -99.9 dB | -145.2 dB | **+45.4 dB** |
| 705.6 kHz | -106.0 dB | -190.9 dB | **+84.9 dB** |

**结论（也是实话）**：44.1k 输出几乎没有整形空间，只能拿到 3.5 dB；
整形的真正用处在 96k 以上。这与"必须先升频再抖动"的行业共识一致。

另外加了一条硬性回归：**任何整形器在任何采样率下，带内噪声都不得劣于 TPDF**
（见 tests/test_dither.cpp 第二节）。

## 2. 两段式升频

### 2.1 为什么要拆

单级 44.1k -> 705.6k（16 倍）时，每输出样本要做 totalTaps/L 次乘加，
而输出样本数是 L 倍，于是总运算量正比于 totalTaps × 输出率。
26 万抽头在 705.6k 下单核根本跑不动（实测 CPU 0.52 倍实时）。

### 2.2 拆法

    44.1k --[第一级 x4，长滤波，承担陡峭过渡带]--> 176.4k --[第二级 x4，64 抽头]--> 705.6k

- 第一级每相位抽头数与单级相同（totalTaps/L），但只跑 1/4 的输出样本
- 第二级只需要在"图像出现处"之前进入阻带，64 抽头足够
- 只在整数升频且 L >= 8 时启用；44.1k -> 96k 是 320/147，单级本来就高效，不启用

### 2.3 实测

| 指标 | 结果 |
|---|---|
| 可听带幅度一致性 | 100 Hz / 1 k / 10 k / 19 kHz 全部差异 **< 0.01 dB** |
| 镜像抑制 | 与单级相当（差 1.1 dB；绝对值受未加窗单点 DFT 的 -80 dB 泄漏底限制） |
| 分块不变性 | 333 / 777 / 1024 帧与整块**逐位一致** |
| CPU 时间 | 单级 5.9 ms -> 两段 2.3 ms（同参数，**2.62 倍**） |

tests/test_two_stage.cpp 覆盖以上四项。

## 3. 7 阶 SDM 调制器：不是"不稳"，是"用错了采样率"

### 3.1 实测事实

| 采样率 | 5 阶 1-bit | 7 阶 1-bit |
|---|---|---|
| DSD64 (2.82 MHz) | 89.4 dB | **2.0 dB（饱和，39444 次保护）** |
| DSD128 (5.64 MHz) | 91.6 dB | **97.4 dB** |
| DSD256 (11.3 MHz) | 107.4 dB | 102.7 dB |
| DSD512 (22.6 MHz) | — | 93.5 dB |

原因：1-bit 量化误差幅度固定为 2.0，7 阶环路在 2.8 MHz 下没有足够的时钟裕度把它压回去。
这不是算法错，而是物理限制 —— 实际产品里 7 阶调制器都跑在 DSD128 以上。

### 3.2 产品化处理

stable_sdm_order(requested, fs)：请求 7 阶但采样率不足时**自动退回 5 阶并打印原因**。

    rtaplay --mod-order 7 --dsd 64
    !! 7 阶调制器在 DSD64 上不稳定（实测会饱和），已自动改用 5 阶

## 4. 多核 DSP

src/dsp/parallel.h 提供 ParallelFor::run(n, fn)，只用在"每声道状态独立"的重活上。

- 用于 rtaplay 的 SDM 调制（每声道一把独立调制器，无共享状态）
- 实测 2 声道 / DSD256 / 200 万样本每声道：串行 72.4 ms -> 并行 38.1 ms（**1.90 倍**）
- **并行结果与串行逐位一致**（0 个不同点）
- DSD128 整曲导出：2 声道 x 16934400 帧（3 秒音频）调制耗时 614 ms（**4.9 倍实时**）

播放路径没有并行化：实时播放的瓶颈是 GPU 重采样（已 4.87 倍实时），
再引入线程调度反而增加抖动风险。
