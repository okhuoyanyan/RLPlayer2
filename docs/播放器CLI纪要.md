# 播放器 CLI 与输出后端纪要（Round 6）

## 1. 已实现

```
rtaplay --list                                        # 枚举端点
rtaplay --gen <out.wav> [秒] [Hz] [位深]               # 生成测试音
rtaplay <in.wav> [--device ID] [--rate N] [--taps N] [--bits N]
                 [--shaper NS9|TPDF|...] [--buffer ms] [--seconds N] [--loop] [--analyze]
```

**已经真的出声了**：WAV → DSP 管线 → WASAPI 独占事件驱动 → 设备。

实测（TASCAM Portacapture X8）：

| 场景 | 输出格式 | 墙钟 | 事件 | 设备实播 |
|---|---|---|---|---|
| 比特完美直通 | 44.1k/24bit | 3.045 s | 32 | 134068 帧 (3.040 s) |
| 升频 4x（65536 抽头） | 96k/24bit | 3.024 s | 32 | 289824 帧 (3.019 s) |

设备枚举正确列出 28 个端点（含禁用/未插入），并正确标出默认设备。

## 2. 🔴 关键未解决问题：超额写入约 6~9%

**现象**（多次复现，非偶发）：

| 缓冲 | 事件间隔 | 写入 | 设备实播 | 超额 |
|---|---|---|---|---|
| 100 ms | 94.3 ms | 4.300 s | 4.040 s | **+6.4%** |
| 100 ms（升频） | 94.5 ms | 3.300 s | 3.019 s | **+9.3%** |
| 100 ms | 95.2 ms | 3.300 s | 3.040 s | **+8.6%** |

**根因**：**事件间隔（~94 ms）短于缓冲时长（100 ms）**。当前实现"每个事件写满一个缓冲"，于是每次多写约 6%。

**如果这 6% 真的被驱动丢弃，那就是丢样 / 跳音——直接伤害音质，必须解决。**

## 3. 本轮排除掉的方案（都是实测否定的，别再试）

| 方案 | 结果 |
|---|---|
| **按 `IAudioClock` 位置节流** | ❌ 位置计数被**量化到缓冲边界**，事件之间根本不推进（首事件恒为 0），用它节流会把每个事件判成"未消耗" |
| 跳过"未消耗"的事件 | ❌ **跳过任何一个事件，事件流立即永久停止**（这是本设备驱动的行为，多次复现） |
| **按 `GetCurrentPadding` 算可用空间** | ❌ 独占模式下 **padding 恒为 0**，等价于"每个事件写满"，无改善 |
| 开流前做预填充 | ❌ 首事件 padding == bufferFrames ⟹ 可用空间 0 ⟹ 跳过 ⟹ 流饥饿停摆 |
| 加大缓冲到 500 ms | ⚠️ 流稳定，但超额比例不变（事件间隔同步变长） |

**四个 API 全部试过**：预填充、`GetCurrentPadding`、`IAudioClock::GetPosition`、跳过事件——没有一条能在"不超额"与"不断流"之间两全。

## 4. 下一步（需要硬件才能定论）

**唯一能判定"6% 到底是被丢弃还是位置计数不准"的方法：环回采集**——
用 SPDIF/模拟输出接回一个 ADC，录下来与源文件逐样本比对。
本机 X8 自带输入，接一根线即可做这个实验（需要你插线）。

在定论之前，**不能声称"比特完美播放链路已完成"**——输出侧还有一个 6% 的疑点。

## 5. 其他

- 修掉一个真 bug：`WasapiOutput::enumerate()` 是静态方法，不会走构造函数，因此 **COM 未初始化 → 列出 0 个端点**。已改为自行 `CoInitializeEx`。
- 修掉 `windows.h` 的 `min/max` 宏污染：`std::min` 被宏替换导致编译失败，已加 `NOMINMAX`。
