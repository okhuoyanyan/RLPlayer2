## 0. 先修正我上一轮的判断

我上一轮说「20 ms 封顶是 DC-Elite 爆音的直接原因」。**1.3.15 已经证伪了这条**：

```
PLAYBUF {"bufferReqMs":100,"bufferMs":100.0,"bf":4800,"per":480,
         "bufPolicy":"requested","initRecipe":"buffer=100.0ms(4800帧),period=10.0ms,event"}
```

缓冲按要求开了 100 ms，**爆音照旧**。所以 20 ms 封顶只是把一个更基础的问题放大了，
不是根因。根因是**写循环的服务粒度**（见 §2）。

## 1. 1.3.15 实测事实

| 量 | N300 | DC-Elite |
|---|---|---|
| 采样率 | 48 kHz（无重采样） | 48 kHz（44.1→48 重采样） |
| 缓冲 / 周期 | bf=**4800**（100 ms）/ per=**480**（10 ms） | 同 |
| 吞吐 `Δpos/Δ墙钟` | **0.959**（pos 4.8 / 5.004 s） | **0.417**（pos 2.1 / 5.037 s） |
| 写成功 / 写 0 | **48 / 229**（失败率 82.7%） | **102 / 471**（82.2%） |
| 归因 | `zp=229 = w0` → **全部 pad=full** | `zp=84`，`zs=0` → **387 次未落入 padFull** |
| `dry` / `dryms` | 43 / 858 ms → **每次 19.95 ms** | 21 / 419 ms → **每次 19.95 ms** |
| `ev` / `evint` | 48 / **105 ms** | 21 / **100 ms** |
| `prod` | 0（生产者从不阻塞） | 0 |

三条关键读数：

1. **`dryms / dry = 19.95 ms`** —— 每一次「设备缓冲空」，我们都要**迟到一个轮询周期（20 ms）**才补上。
   48 kHz 下 20 ms = 960 帧的静音，这就是「啵」。
2. **`evint ≈ 100~105 ms`** —— 设备事件只在**整个缓冲播完**时才来一次，不是每周期一次。
   所以靠事件驱动根本来不及。
3. **`prod=0`** —— DSP/解码从不阻塞，供料侧没问题。**问题在写入时序，不在算力。**

## 2. 根因（代码级）

### 2.1 服务粒度 20 ms ≥ 2× 设备周期（主因）

```cpp
// src/audio/render_loop.h:312（1.3.13 行号）
sink.wait_event(20);                    // ← 睡到事件或 20ms
const size_t w = sink.write_available(pend.data(), pendFrames);
```

- 设备周期 `per` = 480 帧 = **10 ms**；轮询上限 = **20 ms** = **2 × per**。
- 循环只有在「被唤醒」时才有机会写。设备在两次唤醒之间已经消耗掉 1~2 个周期，
  `room` 一旦不足一个周期就被量化成 0 → `w0`。
- 实测 `dryms/dry = 19.95 ms` 与 20 ms 完全吻合：**每次都是等到下一个轮询才发现缓冲空了。**

### 2.2 先等待、后写入，天然制造空窗

```cpp
// 顺序：睡 → 写
sink.wait_event(20);
write_available(...);
```

设备把整块缓冲取走后（`pad → 0`），我们必须先「醒过来」才能补写；
这中间就是 §2.1 那 20 ms。

### 2.3 只有 `room ≥ per` 才写（次要，但放大问题）

```cpp
// src/audio/wasapi_out.h:617-623
if (per > 1 && per <= bufferFrames_ && (toWrite % per) != 0)
    toWrite = (toWrite / per) * per;     // 不足一个周期 → 归零
```

DC-Elite 的 `w0=471` 里只有 `zp=84` 是「缓冲满」，其余 387 次是**有空间但不足一个周期**，
被量化成 0 白白错过。DC-Elite 每次只写进 988 帧 ≈ 2 个周期（`102 写 × 960 = 97920 帧 ≈ pos 2.1 s`），
所以它的吞吐只有 0.42。

### 2.4 STARVING 判据仍然失明

`STARVING` 用「吞吐率」判罚（`render_loop.h:366-412`），N300 实测 0.959 > 0.90 阈值，
DC-Elite 0.417 才会触发。**N300 这种「0.96 但每 116 ms 断 20 ms」它永远看不到。**
真正能证明问题的判据是 `dryms/dry`（本次新加的），但还没接进任何判定。

## 3. 修改方案

按优先级，四项。**P0 不做，其它都没意义。**

### P0-1 服务粒度：20 ms → ≤ per/2，且「先写后等」

```cpp
// 循环体顺序改为：写 → 等
const int waitMs = std::max(1, (int)(per * 1000.0 / rate / 2));   // per=10ms → 5ms
size_t w = sink.write_available(pend.data(), pendFrames);         // 先补满
if (w == 0) sink.wait_event(waitMs);                              // 只有没写成才睡
```

- 90 kHz 以下建议 `≤ 2 ms`；96 kHz/per=960 时 `≤ 5 ms`。
- 目标是**任何时刻都不让缓冲掉到 0**，而不是「掉了再补」。

### P0-2 不再依赖事件：用 IAudioClock 预测消耗，主动补料

事件间隔实测 100 ms，靠它等于每 100 ms 才补一次。改为：

```cpp
// 每次循环：
//   1) IAudioClock::GetPosition 取设备已渲染帧数 rendered
//   2) backlog = writtenFrames - rendered
//   3) 目标水位 target = bufferFrames * 0.75
//   4) 若 backlog < target，立即写 min(target - backlog, room)
```

padding 只用来判断「最多能写多少」，不再作为「是否需要写」的唯一依据。
这样即使事件不来，也不会停摆（保住 P1 纪要里「跳过事件不会让流永久停止」那条结论）。

### P0-3 量化：允许小于一个周期的写入

- 规则改为：**只有当 `room == 0` 时才放弃**；`0 < room < per` 时照写（WASAPI 独占的
  `GetBuffer` 只要求 `≤ room`，不要求整周期；整周期要求是部分驱动的实现细节，
  失败时按 `AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED` 回退到整周期）。
- 若驱动确实拒绝非整周期（返回 `E_INVALIDARG`），则记录一次「该端点要求整周期」到学习缓存，
  对该端点回退整周期策略——而不是对所有端点一刀切。

### P1 判据：把 dry 接入 STARVING

```
判据D：dryms / dry > 1.5 × per_ms  且  dry ≥ 2（10 分钟内）⟹ 判「供给不足」
```
现有吞吐率判据保留不动（不调阈值）。判据 D 只**报告**，不触发回退共享。

### P2 缓冲策略（上一版 C1 保留，但降级为辅助）

「尊重用户设置 + 自适应回退」仍然要做（MOTU 防护），但它**不是**本次爆音的修复项。

## 4. 验收数字（1.3.15 现状 → 目标）

| # | 判据 | 1.3.15 实测 | 目标 |
|---|---|---|---|
| M1 | N300 吞吐 | 0.959 | **≥ 0.995** |
| M2 | DC-Elite 吞吐 | **0.417** | **≥ 0.995** |
| M3 | `dry`（10 min） | 86 次/10s 量级 | **0** |
| M4 | `dryms/dry` | 19.95 ms | **< 1.5 × per（< 15 ms），最好 0** |
| M5 | 写 0 占比 | 82% | < 10%（缓冲大时属正常，见下） |
| M6 | `zp+zs+other == w0` | **不闭合**（DCE 差 387） | 闭合 |
| M7 | 门禁 | — | 构建 0 error / ctest 全绿 |

⚠️ **M5 要小心**：缓冲大时 `w0` 高是正常的（上一轮 1.3.13 的 B 组实测 zp 占 80.5% 却健康）。
判罚只能用 `dry` 和吞吐，不能用 `w0`。

⚠️ **M6 是本次新发现的缺陷**：DC-Elite `w0=471` 但 `zp=84`、`zs=0`，差 387 次**没有归因**。
要么是 `write_available` 里 `GetCurrentPadding` 失败提前 return（未进 classify），
要么是 STAT 没打 `other`。先修遥测闭合，再谈判据。

## 5. 测试（mock 驱动，不开设备）

| 用例 | 断言 |
|---|---|
| 服务粒度 | 注入 per=10 ms 的 mock sink，循环必须在 ≤5 ms 内补写；`dry` 恒为 0 |
| 先写后等 | mock 记录调用序列，`write_available` 必须早于 `wait_event` |
| 部分写入 | `room=300, per=480` → 必须写 300（旧行为写 0） |
| 从空补满 | mock 模拟「整块被取走」，循环必须在 1 个周期内补回 |
| 判据 D | 注入 dry 风暴 → 报警；健康 sink → 不报警 |
| 归因闭合 | 任何 0 写入都必须落进 zp/zs/other |
| 回归 | 48/96/192 kHz × 20/100/200 ms 参数化 |

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 轮询变密（2–5 ms）增加 CPU | 空闲时仍靠事件阻塞；只在「有数据且未满」时忙轮询 |
| 非整周期写入不被某些驱动接受 | 失败即学习并回退整周期，逐端点记忆 |
| IAudioClock 位置不准（部分驱动） | 与 padding 交叉校验；不一致时以 padding 为准 |
| 改动触及实时路径 | 先在 mock + 真机短跑验证，再长测 |
