# 端点漂移估计修正纪要（Round 23）

代码：[tools/rtanet_rx.cpp](tools/rtanet_rx.cpp)

## 1. 修掉的问题：端点虚报漂移 +291.6 ppm

**原因**：端点在用「**包到达时间**」做最小二乘拟合。而发送端是**突发式**发送的
（每批 4 包 = 512 帧然后 sleep），到达时间因此带有强周期性抖动，
拟合器把这部分抖动误当成了晶振漂移。回环上真实漂移应为 0。

**修复**：改用「**缓冲水位趋势**」——即 `已收到帧数 − 已交付帧数` 的长期斜率。
这才是物理上真正驱动流控的量：水位在涨说明发送快于消费，反之亦然。

```cpp
bufHist.emplace_back(nowSec, (double)framesIn - (double)framesOut);
// 5 秒窗口最小二乘斜率 → frames/sec → ppm
return slopeFramesPerSec / (double)fmt.rate * 1e6;
```

## 2. 修复效果

| | 修复前 | **修复后** |
|---|---|---|
| 末次漂移读数 | +291.6 ppm | **−0.0 ppm** |
| 逐位完美性 | ✅ 保持 | ✅ 保持 |

回环上真实漂移为 0，现在读数正确归零。**这才是可信的估计器。**

## 3. ⚠️ 新暴露的问题：文件 sink 下外环失效

修复漂移估计后，最终修正仍然爬到 **+158.5 ppm**。原因不在控制器，而在**测试装置的 sink**：

- 文件 sink **瞬时消费**所有交付的数据 ⟹ `framesOut` 一路追平 `framesIn`
- 于是上报的水位恒为 **0.0 ms**，而目标是 200 ms
- 外环（PI）看到"水位远低于目标"，就持续加大发送速率 ⟹ 修正量爬到高位

**这不是控制器缺陷，是文件 sink 不按实时节奏消费导致的测量失真。**
真实场景下 WASAPI 独占输出的 `framesOut` 由 DAC 时钟驱动，水位是有意义的。

**验证这个闭环需要**：
1. 给文件 sink 加**实时节奏**（按 1/rate 秒每帧推进 framesOut），或
2. 直接在真实 WASAPI 输出上跑（但需遵守铁律 1，且要有 DAC）

**在此之前，不能声称闭环保真已通过真实路径验证。** 可以确认的是：

- ✅ 状态回传协议工作正常（73 条 / 8 秒）
- ✅ 漂移估计准确（回环上正确报 0）
- ✅ 逐位完美性未被破坏
- ❌ 外环在文件 sink 下无法被正确验证
