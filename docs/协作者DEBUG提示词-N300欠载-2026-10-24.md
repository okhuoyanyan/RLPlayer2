### 0. 背景：问题到底被确认到什么程度（数字都来自你 2026-10-22 的日志）

| 项 | 值 | 来源 |
|---|---|---|

| 写入尝试 | w0=205 次写 0，wr=41 次写成功（成功率 16.7%，每次成功恰写满 9600 帧） | STAT 行 |

| clip | **0**（10.5 s 内零个满幅样本） | STAT 行 |

**已经排除的形态**（别再往这些方向查）：
1. **不是削波**：clip=0，且 preAtten 已把过采样峰值压到 0.98；
2. **不是 LNS15 量化器锁死**（锁死会满幅连续噪音、clip 暴涨、peak≈1；现场是间歇断音、peak=0.486）；
3. **不是 DSD 调制器锁死**（dsd=0 / modOrder=0，走的是 PCM + LNS15，没有调制器）；
4. **不是解码失败**（ffmpeg → pcm_s24le 成功，frames=9490181，还能写出 41 个整缓冲）；
5. **不是「设备打不开」**（流开成功了，STAT 也出来了）。

**仍未定案的**：吞吐 0.39 只能说明「设备没拿到足够数据」，但至少有三种互斥成因，必须由**新遥测**区分：
- ① 设备缓冲满（pad == bufferFrames，设备不收）→ zp；
- ② 我们喂不上一个周期 / 整周期量化后归零（avail < per，我们供不上）→ zs；
- ③ 其它（可用空间不足一个周期、GetCurrentPadding 失败等）→ zr=other。

⚠️ 关键教训（本项目反复踩过）：**「日志里没有 error」不等于正常**。旧的 RENDERFAIL 判据只数「连续 201 次写不进去」，而现场每 257 ms 就成功一次、计数被清零，所以永远不报错 —— 这正是「修了几次都没修好」的原因之一。

另外两个你会用到的既有能力：
- **独占格式阶梯**：紧凑 24 → float32 → 32容器/24有效 → 32int（`wasapi_out.h:376-389`），实际选中的格式在 `fmt_note()`；**但「哪个 Initialize 配方成功」目前不落日志**（`wasapi_out.h:394-400`），这是已知盲点，第 2 节要补。

### 4. 第 2 步：先补遥测（必须；单独一个 commit，先于任何修法）

现在缺的不是「猜修法」，而是**能定案的数**。请把下列字段落进日志（日志量可控，不需要开 debugger）：

**A. 开流时（写入 PLAY 行或紧随其后一行）**
- `bufferFrames`（GetBufferSize）、`per`（GetDevicePeriod × rate 取整）、`GetDevicePeriod` 原始 100ns 值；
- **成功的 Initialize 配方**（`wasapi_out.h:394-400` 的 `tries[]` 下标 + 文案：buffer=period=100ms/event、buffer=100ms/period=默认、全默认...）；
- `fmt_note()`（独占格式）、是否触发对齐重试 `realigned`、最终实际请求的缓冲 ms（注意 GUI 路径是 20 ms 封顶后的值，要如实打印「请求 X ms → 实际 Y ms」）；
- `GetMixFormat` 的共享混音格式（用于对比；只读、不开流）。

**B. STAT 行（每次追加，保留现有字段）**
- `dry=`：从起播 500 ms 之后开始计，**当次轮询读到 pad==0 且手里还有待写数据**的次数（这就是「设备空转」次数，每 1 次 ≈ 一次可闻「啵」；这是把主观听感变成数字的关键判据）；
- `dryms=`：累计处于 dry 状态的墙钟毫秒；
- `per=`、`bf=`（bufferFrames）、`zr=` 最近成因、`zp/zs`（已有）；
- `ev=`（wait_event 返回 true 的次数）、`evint=`（最近事件间隔 ms 的中位数或均值）；
- `prod=`：生产侧（pull_chunk 从队列拿到块）最长阻塞 ms / 累计阻塞 ms（若记录成本高，至少记最近 5 秒内最大值）。

**C. 写失败明细（前 200 次逐条，之后只统计）**
每次 `write_available` 返回 0 时打印一行：`t=`（相对起播秒）、`pad=`、`room=`、`per=`、`avail=`（pendFrames）、`toWrite=`（量化后）、`gb_hr=`、`zr=`。
→ 有了这 200 条，①②③ 立刻可判，不必再猜。

**D. rtaplay 也加同样的 `zp/zs/dry`**（`tools/rtaplay.cpp` 状态行，约 859 行附近；它的写模型是 `pump_consumed`，见 `wasapi_out.h:551-578`），否则第 5 节 E1 的 A/B 没有可比数。

**硬要求**：这些是纯观测，**不得改变任何写入/调度/DSP 行为**；先把「能测」做好，再谈修。

### 6. 第 4 步：定位与修法（允许的方向 + 红线）

**先写判据再改代码**（项目铁律 3：这个项目被「判据本身定义错」误导过多次）。

可能的修法方向（按 E1–E6 的结果选，不要预设答案）：
1. **缓冲策略**：把 `tools/rtaweb.cpp:438` 的「无条件封顶 20 ms」改成「尊重用户设置 + 失败自适应」：
   先按请求值开流；若在 N 秒内出现 `zp` 暴涨 / 流不推进（MOTU 形态）→ 关闭重开为 20 ms，并在日志/UI 如实说明「该设备已降级到 20 ms」。
   **不允许**为了修 N300 把 MOTU 那条修复删掉。
2. **写模型**：若 E1/E4 指向 render_loop 的「20 ms 轮询 + 整周期量化」，改为「按已消耗量写」：
   以 `GetCurrentPadding` 为主、`IAudioClock` 为辅，写 `min(room, avail)` 且保证 period 整数倍；轮询间隔至少要明显小于 per（per=20 ms 时，20 ms 轮询必然相位抖动）。
3. **供料侧**：若 zs 高 → 提高渲染线程优先级（`AvSetMmThreadCharacteristics` 之类，需谨慎）、增大预攒周期数、把重 DSP 移出渲染线程、必要时 GPU 卷积。
4. **事件驱动**：若 E4 证明事件不可靠 → 回到「小睡 + 轮询」但保证不跳过必写窗口；任何改动都要保住「事件丢失不会让流永久停摆」这条既有结论。

**红线（违反任何一条 PR 不合并）**：
- 不改 DSP 数学（滤波器/量化器/调制器/卷积数值），除非根因明确指向它 —— 那时必须单独 PR，并按铁律 7 补满「过载后能恢复」的测试；
- **不许调高 STARVING 阈值、不许关掉 STARVING/RENDERFAIL** 让日志变干净；
- 不许把「自动回退共享 + 从头重播」当解决方案（用户要 bit-perfect，回退是降级）；
- 不动 `src/dsp`、`src/engine`、`src/net`、`src/meta` 里引入 `<windows.h>`（`tools/check_platform_boundary.ps1` 会红）；
- 不加会让 ctest 打开音频设备/放声的用例；
- 不改版本号、不动别人的分支、不 force-push main。

### 13. 日志怎么取（自己看的时候）

- `rlplayer-playback.log` 在 exe 同目录（启动器/服务都是），超过 4 MB 轮转，保留 3 份；
- 设置 → 「诊断」→「导出诊断包（.zip）」= 一次拿到 `rlplayer-diag.json` + 3 份 playback log + launcher log；
- `STAT` 每 5 秒一行；`PLAY` 行是 JSON，包含当次全部设置与信号链数字（ispPeak/preAtten/fmt 等）；
- `STAT` 里的 `pad` 是**上一次轮询**的水位（打印在 wait_event 之前），别当成打印瞬间的值 —— 这个坑 2026-10-22 已经踩过。
