# HQPlayer 的「秘诀」到底是什么（Round 73 深度分析）

> 用户的质疑：我们现在做的这些，就是 HQPlayer 能当「公认音质最好」的全部秘密吗？
> 诚实的回答是：**不是。而且我一直在优化一个对听感几乎无影响的指标。**

## 1. 我犯的错：优化错了指标

我一直在追求**阻带衰减**（−189 dB、−248 dB、−249 dB）。

但阻带深度在 −120 dB 以下对听感**几乎没有意义** —— 任何 24-bit 系统的本底噪声约 −144 dB，
而人耳在正常音量下的动态范围远小于此。把阻带从 −189 dB 做到 −249 dB，听感上是零差异。

**真正影响听感的是这几件事（按重要性）：**

| 维度 | 为什么重要 | 我们的现状 |
|---|---|---|
| **1. SDM 调制器的阶数与噪声整形形状** | DSD 输出时，量化噪声是否被推到音频带外，直接决定「安静、通透、无毛刺」 | ⚠️ **只有 5 阶可用，7 阶不稳定** |
| **2. 升频后的最终采样率** | 让 DAC 内部的廉价插值滤波器被绕过，交给我们的高质量滤波 | ✅ 有，但只有 PCM 到 705.6k / DSD 到 256 |
| **3. 过渡带的位置与形状** | 截止频率离 Nyquist 多远、滚降多陡、有没有切趾(apodizing) | ⚠️ 有参数，但**用错了评价标准** |
| **4. 群延迟/相位的一致性与振铃分布** | 决定瞬态与「空间感」 | ✅ 最小相位已实现 |
| **5. 抖动噪声整形的阶数** | 24-bit 以下输出时的底噪形状 | ✅ NS9/LNS15 |
| **6. 系统级时序** | 线程优先级、CPU 亲和、定时器粒度、内存锁页 | ⚠️ 本轮才开始做 |
| **7. 输出路径的零污染** | 独占模式、事件驱动、无任何系统音效 | ✅ 已做到 |

## 2. HQPlayer 真正难被复制的地方

### 2.1 SDM 调制器（最大差距）

ASDM7EC 系列是 HQPlayer 的招牌。它的关键不在于「7 阶」这个数字，而在于：

- **7 阶噪声整形**把量化噪声推到 100 kHz 以上，音频带内可低到 −120 dB 以下
- **EC = Extended Compensation**：额外的前馈路径补偿高阶环路的稳定性裕度
- 能在 **DSD256/512（11.2/22.5 MHz）** 下实时运行
- 高阶调制器极易发散，需要精细的环路滤波器设计（如 Chebyshev II 型 NTF，H∞ ≈ 1.5~2）

**我们的现状**：5 阶可用（DSD5 1-bit 带内 SNR 86.2 dB），7 阶在 0.5 幅度下发散。
**这是最大的差距，也是最值得投入的地方。**

### 2.2 为什么它能跑那么长的滤波器

DSD512 意味着 22.5 MHz 的处理率。这需要：

- 多核并行（HQPlayer 的 Multicore DSP / DSP pipelines / Blocks per cycle）
- **两段式升频**（先到中间率，再到最终率）—— 大幅降低总运算量
- GPU 卸载（CUDA，卷积与部分滤波）

**我们的现状**：单线程处理；GPU 只用于卷积。长滤波器（sinc-M 524287 抽头）能跑但只能离线。

### 2.3 「听感」而非「指标」的滤波器设计

poly-sinc-ext2、poly-sinc-gauss-* 这些滤波器的差异**不在阻带**，而在：

- 过渡带的**形状**（高斯 vs 切趾 vs 陡降）
- **切趾（apodizing）**：压制 ADC 阶段留下的前振铃
- 通带到阻带的**能量分布**

这些差异在频谱图上看起来都「很平」，但听感差异明显。

## 3. 为什么「升频」能让 DAC 更好听（物理原因）

这是理解 HQPlayer 价值的关键，很多人以为是玄学：

**几乎所有 delta-sigma DAC 内部都有一个廉价的数字插值滤波器**（通常 8× 过采样 + 一个短 FIR）。
这个滤波器为了成本和延迟，过渡带很宽、阻带很浅（常常只有 −40~−60 dB），
会在音频带内留下**镜像与混叠**。

如果你在软件里先升到 705.6 kHz 或 DSD256，DAC 内部的插值滤波器就会被**绕过或大幅简化**，
于是那些镜像与混叠就不产生了 —— **这是实测可验证的，不是听感玄学。**

所以 HQPlayer 的真正价值是：**用软件里的高质量滤波器，替换掉 DAC 里的廉价滤波器。**

## 4. 我们的实际差距（诚实清单）

| 差距 | 影响 | 优先级 |

## 5. 新需求：流媒体接入（Navidrome / Emby）

### 设计原则：**只取原始文件，绝不接受转码流**

这是「不降低音质」的唯一正确做法：

| 服务 | 原始文件接口 | 绝不能用的接口 |
|---|---|---|
| **Navidrome**（Subsonic 兼容） | `/rest/download?id=xxx` 或 `stream?format=raw` | `stream?maxBitRate=...`（会转码） |
| **Emby** | `/Items/{id}/File?api_key=` 或 `/Videos/{id}/stream?static=true` | `?static=false`（会转码） |

**流程**：

```
HTTP 拉取原始字节 -> 内存/临时文件 -> read_any 本地解码 -> 完全相同的 DSP 链 -> 输出
```

关键点：**流媒体与本地文件走完全相同的解码与 DSP 路径**，所以音质与本地播放**完全一致**，
不存在「流媒体音质差一点」这回事 —— 只要拿到的是原始文件。

还要做：
- 校验返回的 Content-Type 与文件大小，若是转码流则拒绝并报错（宁可报错也不要悄悄降质）
- 缓存已下载的曲目（避免重复拉取）
- 播放时提前预取下一首（与本地队列共用预解码机制）
