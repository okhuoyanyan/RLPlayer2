# 播放管线整合纪要（Round 5）

代码：[src/audio/wav.h](src/audio/wav.h)、[src/engine/pipeline.h](src/engine/pipeline.h)　测试：[tests/test_pipeline.cpp](tests/test_pipeline.cpp)

## 1. 三条路径判定（这是"比特完美"的工程实现）

| 路径 | 触发条件 | 做法 | 可证性 |
|---|---|---|---|
| **逐位直通** | 不升频、不整形、输出位深 == 输入位深、整数格式 | 原始整数样本**原样搬运** | 逐位可证 |
| **无损展宽** | 输入位深 < 输出位深、不升频、不整形 | 样本值左移补齐（16→24 即 `raw<<8`） | 数值不变，逐位可证 |
| **完整 DSP** | 升频 / 整形 / 位深缩减 任一启用 | 转 double 处理，最后按目标位深重新量化 | 由客观指标保证 |

**关键设计**：`AudioBuffer` 内部保留**原始整数样本**，而不是只存归一化浮点。
浮点往返会引入不可逆的舍入，**那样根本无法证明比特完美**——这是很多播放器"声称比特完美却做不到"的根因。

## 2. 实测结果（全部通过）

| 验证项 | 结果 |
|---|---|
| WAV 24-bit 立体声 写入→读回 | **逐位相同** |
| 直通路径（16 / 24 / 32-bit） | **逐位相同** |
| 16 → 24-bit 无损展宽 | **错位样本 0** |
| 升频 44.1k → 176.4k（4x，65536 抽头） | 输出帧数正确、采样率正确 |
| 升频后基波幅度 | **−6.0179 dB**（期望 −6.0206 dB，误差 0.003 dB） |
| 16-bit 输出样本落在量化网格上 | **严格通过** |

## 3. ⚠️ 未解决项（明确记录，不粉饰）

**升频后拟合残差 1.1e-4（−79 dBFS，SNR 仅 70 dB）**，远高于本链路的预期。对照数据：
- 重采样器**单独测试**：谐波 −134 dBc、镜像 −158 dBc、DC 增益精确到 1e−10
- 滤波器原型：通带纹波 0.0000 dB、阻带 −189 dB

嫌疑方向（尚未定位）：
1. 测试信号自身注入的 ±1 LSB 抖动
2. 拟合频点与段长不整除（339.1156 个周期）导致的拟合残差
3. 管线的 double↔整数往返在某处引入了额外误差

**当前以 60 dB 作为回归基线。** 测试"通过"不等于问题已解决——已在测试源码中写明这一点，避免后续被误认为已验证。

## 4. 本轮踩的坑（**三次假失败全部来自测量方法，而非 DSP**）

时域逐点比对"输出 vs 零延迟理想正弦"得到 −9 dBFS 的残差，我一度以为是 DSP 坏了。实际是：

| 尝试 | 残差 | 真实原因 |
|---|---|---|
| 不补偿延迟 | −9 dBFS | 群延迟 32767.5 个输出样本 |
| 用 `(T_−1)/2` 估算延迟 | −26 dBFS | 公式错了：原型长度是 `T_·L`（偶数），群延迟应为 `(T_·L−1)/(2L)` |
| 用精确延迟补偿 | −44 dBFS | 还有 ~0.5 样本的残余相位误差 |
| 改用单频点 DFT | −94.3 dBc | 被 Hann 窗泄漏地板限制 |
| **改用最小二乘正弦拟合** | **−79 dBFS** | 延迟无关、无泄漏——**这才是真实残差** |

**教训**：时域逐点比对会被延迟估计的零点几个样本误差完全支配，用它去判定 DSP 精度是无效的。
延迟无关的频域判据（最小二乘拟合 / 相干 DFT）才是正确工具。

顺带修掉一个真实缺陷：`latencyInputSamples()` 原先返回 `(T_−1)/2`，在 L=4 时偏差 3.5 个输出样本（997 Hz 上约 7° 相位误差）。已改为精确公式。

## 房间校正自动应用（B3，2026-10-27，用户 261027-05）

**用户原话**：「既然已经基本搞定了，**接上就是了**」——向导生成 `correction-<布局>.json` 之后，
播放链路必须自己挂上，而不是让用户去「声音校准 → 校正文件 → 脉冲响应 IR」手动挑文件。

### 决策链（每一环都能从 `/api/signal` 的 `roomCorr` 读到结论）

| 顺序 | 条件 | 结果 |
|---|---|---|
| ① | 设置项 `roomcorrauto=1`（默认） | 0 ⟹ `applied=false`，`why="设置项「自动应用校正」已关闭"` |
| ② | 用户手动配了 `ir=<wav>` | 以手动为准（`manual=true`，`why="已手动指定脉冲响应 IR…"`）—— 绝不悄悄覆盖用户的选择 |
| ③ | `data\roomcorr\correction-<当前输出布局>.json` 存在 | 不存在 ⟹ `mismatch=true`，`why` 列出磁盘上**实际有哪些**布局 |
| ④ | 文件可读、每声道 FIR 非空 | 否则不应用并如实报错（不猜、不给半套） |

**布局从哪来**：当前输出声道数 → `room_layouts()` 里同声道数的布局名（2.0/2.1/5.1/7.1/5.1.2/7.1.4）。
8 声道同时对应 7.1 与 5.1.2，两个候选都按磁盘实际文件挑。

**采样率**：校正集 `fs` ≠ 源采样率时先 `ir_resample`（卷积在重采样之前，卷积器看到的是源采样率；
与手动 IR 的既有规则 261024-05 A2 同一条）。

### 实现位置

- `tools/rtaweb.cpp`：`roomcorr_auto_prepare()`（前置声明在 `play_one_impl` 之前，实现在 roomcorr 工具区）、
  `PlayParams::roomCorrAuto`、`/api/settings` 白名单与 `injectKv("roomcorrauto","1")`、
  `/api/signal` 的 `roomCorr` 对象。
- `src/net/ui_script.h`：声音校准页的「自动应用校正」开关 + `rcAutoSync()` 状态行；
  信号链新增「房间校正 已应用（文件 X）」/「未应用（附原因）」/「已关闭」三种节点。
- 日志：每次播放一行 `ROOMCORR-AUTO applied|skip want=<布局> ch=<N> file=… taps=… setFs=… why=…`。

### 实测（build-be1，2026-10-27）

| 场景 | `roomCorr` | `bitPerfect` | `dspBlockMs` |
|---|---|---|---|
| 2.0 集在盘上、自动应用开 | `applied=true, file=correction-2.0.json, taps=8192` | `no`（原因「房间校正（correction-2.0.json）」） | 0.486 |
| `roomcorrauto=0` | `applied=false, why=设置项已关闭` | `yes` | 0.012 |
| 盘上只有 5.1 集、按 2.0 输出 | `mismatch=true, why=…磁盘上只有 5.1…` | `yes` | 0.012 |
| 手动 `ir=` 同时存在 | `manual=true, applied=false` | `no`（原因「IR 卷积」） | — |

`dspBlockMs` 从 0.012 → 0.486 ms/块 是**卷积真的进了链路**的旁证（8192 抽头 × 4096 帧 CPU 分块卷积）。
