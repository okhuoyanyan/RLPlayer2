# 真机联调记录：输入采集 + P5 投放（2026-10-23）

> 用户授权：麦克风 **Widget B** 可用且已设为默认；数字播放器 **192.168.50.109** 已切到 MPD/UPnP Renderer 模式；
> 音箱已物理关闭，允许直接调用声卡实测。

## 一、输入采集（Widget B）—— ✅ 端到端通过

`GET /api/input/devices` 正确枚举 4 个端点，**Widget B 被标为默认麦克风**：
```json
{"name":"麦克风 (Widget B)","state":1,"isDefault":true,"isLoopback":false,"mixRate":48000,"mixChannels":2,"mixBits":32}
```

实测（`POST /api/input/start` `mode=record&dev=Widget+B&seconds=3`）：
```json
{"running":false,"device":"麦克风 (Widget B)","rate":48000,"channels":2,"seconds":3,
 "frames":144000,"water":0,"overflow":0,"underflow":0,"posClips":0,"negClips":0,
 "outFile":"...\\recordings/cap-20261023-141724.wav","rmsDb":-85.39,"peakDb":-73.88,"error":""}
```
- **144,000 帧 = 48000 × 2ch × 3s，精确无欠载/溢出/削波**；
- RMS −85.4 dB / peak −73.9 dB（音箱已关的静室，数值合理，非零说明确实收到信号而非假数据）；
- WAV 正常落盘到 exe 目录 `recordings\`。

**参数说明（踩到的坑，写进交接）**：`/api/input/start` 的设备字段名是 **`dev`**（不是 `device`），
传错会被静默忽略并回落到默认端点（我第一次就踩了，表现为"指定 Widget B 却打开了 Realtek Center"）。
→ 待改进：**参数名不认识时应当报错而不是静默回落**（已记入未解决项）。

## 二、P5 UPnP 投放 —— 控制面 ✅ / 供源侧被网络隔离 ❌

见 `docs/P5-UPnP端到端实测-2026-10-23.md`（完整证据链）。摘要：

| 环节 | 结果 |
|---|---|
| SSDP 组播发现 | ❌ 本机网络零响应（手写 M-SEARCH 亦然） |
| 直连描述 URL | ✅ `--dev http://192.168.50.109:49152/` 成功识别 `N1000_UPNP`（upmpdcli 1.4.12 + MPD 0.22.0） |
| SetAVTransportURI / Play | ✅ 200 OK，GetTransportInfo → PLAYING |
| 设备拉流 | ❌ MPD：`Failed to decode http://192.168.50.140:8912/... CURL failed: Connection timed out` |
| 对照实验 | 换最简 Python http.server 仍超时；按端口+按程序放行防火墙仍超时；**从未观测到设备入站连接** |

**判定**：设备→开发机 TCP 入站被阻断（AP/客户端隔离）。代码侧无需修改；已把 `rtacast --list` 空发现时的提示改为**直接给出直连用法**。

**打通后复测命令**：
```powershell
rtacast --file <音频> --dev http://192.168.50.109:49152/ --seconds 15
```
判据：MPD `status` 的 `time:` 推进 + `state: play` + 本机看到设备建立的 TCP 与 `Range` 请求。
