## 0. 一句话结论

**做，而且必须做 UAC2 直连 + GPU 升频。** 但有三条**数学上的硬约束**必须先满足，

## 2. 数学约束（这是本项目最核心的技术判断）

### 2.1 为什么 float32 直接算一定失败

| 运算 | float32 能否精确 |
|---|---|
| 乘积 `a*b` | ✅ 可（用 `fma(a,b,0)`） |
| 累加 `x + c`（c 为主项） | ✅ 绝对精确（尾数被完整吸收） |
| **乘累加（FMA）** | ⚠️ **不可精确**（乘积先舍入） |
| **几十项同量级部分和** | ❌ **必然损失** |

**已有实证**：`CMakeLists.txt:35-36` 记录 —— FMA 收缩让 **EC-7@DSD512 带内 SNR 从 121.8 dB 塌到 60.9 dB**（239 条 vfmadd 融合）。
⟹ **凡涉及 FMA 融合或长累加，float32 必然出问题。**

### 2.2 信息论层面的死结

**24 bit 的容器装不下 130 dB 阻带（>21 bit）的滤波器乘以 24 bit 信号的结果。**
这不是实现问题，是信息论问题。
⟹ **「float32 GPU 升频 + 逐位等价」在数学上无解，怎么做 kernel 都没用。**

### 2.3 唯一成立的路径：float32 模拟更高精度

用 **double-double**（(hi, lo) 两个 float32）：
- 硬件基础：`fma()`（Adreno 支持 fp32 FMA，这正是硬件的本来用途）
- 有效精度：2 × 24 = **48 bit**（低于 float64 的 53 bit，但远超 24 bit）
- 理论基础：**Error-Free Transformation**（two-sum / two-product / Dekker），**可以写出「误差恒为 0」的证明**
- **已有代码基础**：`tools/gpubench.cpp:23-28` 的 `fmaDF` 就是这套东西

### 2.4 开销真相（不是「6 倍」，别吓自己）

| 方式 | 相对开销 | 备注 |
|---|---|---|
| float32 直接 | 1× | 基准 |
| **double-double 全模拟** | **6×** | 每次乘加 3 乘 + 3 加 |
| **多级结构下「只对乘积模拟」** | **2.5~3.5×** | 级内主项 O(1)，小项天然被吸收，不需要模拟 |

**6× 是悲观上限。** 因为我们本来就是 4 级级联（×16 = 2 的幂），
**每级内部可以证明无需全精度**，只有乘积需要模拟。

### 2.5 跨平台一致性：CPU 侧同样要守

| 风险 | 现状 | 处置 |
|---|---|---|
| FMA 收缩 | ✅ `CMakeLists.txt:41` 已有 `-ffp-contract=off` | 保持 |
| **`-ffast-math` 含 `-fassociative-math`** | ⚠️ `CMakeLists.txt:31` | **❗必须修**：去掉 reassoc，否则 ARM 与 x86 求和顺序不同，同源码不同结果 |
| 「逐位等价」的判据定义 | ⚠️ `tests\test_modulator_rates.cpp:252-260` 已记录 | **只能在同二进制内比**；跨 CPU 的判据必须是「与 IEEE-754 double 参考值逐样本相等」，不是「与某个已录哈希相等」 |

## 3. UAC2 直连（结论：正确路线）

### 3.1 为什么 UAC2 是对的

| 事实 | 意义 |
|---|---|
| UAC2 是 USB-IF 国际标准 | **一份协议栈覆盖所有 UAC2 DAC**，不需要为每家厂商适配 |
| 速率协商标准化 | ENDPOINT_CONTROL 请求（GET_CUR / GET_MIN / GET_MAX）读能力，**不猜** |
| **isochronous feedback endpoint** | 规范定义（全速 Q10.10 / 高速 Q16.16），**按 DAC 反馈调速 = bit-perfect 的最后一道保障** |
| 已有可验证先例 | Vox Machina（2026-05）、USB Audio Player PRO，均在 Android 上做到 UAC1/UAC2 + DoP + Native DSD，**无需 root** |

### 3.2 必须提前知道的两个风险

1. **等时传输没有重传**：丢了就丢了。⟹ **发送缓冲策略必须比 WASAPI 更保守**。
   好消息：N300 那套「缓冲积压趋势 + L1/L2 自适应回退」经验可直接复用。
2. **Native DSD 的格式描述各家不同**（类似 ASIO 上的「类型 33 / MSB1」坑）：必须做能力探测 + 失败回退 DoP。

### 3.2.1 ⚠️ 2026-10-28 补充：Android 公开 USB API **不支持等时传输**（推翻原假设）

> **这一条修正了本文档 §3 与 P6 的隐含假设。** 起因：评估「USB bulk」时查证发现。
> 详见 `docs\USB-Bulk与移动HiFi-评估.md` §5。

**事实**（三处独立证据）：

| 证据 | 内容 |
|---|---|
| Android 官方 `UsbRequest` 文档（页面更新于 2026-08-03） | 「UsbRequests can be used to transfer data on **bulk and interrupt** endpoints.」—— 无 isochronous |
| 平台常量 `USB_ENDPOINT_XFER_ISOC` | 注释为「Isochronous endpoint type (**currently not supported**)」 |
| StackOverflow 长期结论 | 只能 native + libusb，且要用 `UsbDeviceConnection.getFileDescriptor()` 的 fd 交给 libusb |

**⟹ 实现方式必须改成：**

```
Java/Kotlin：UsbManager 枚举 + requestPermission → 拿到 UsbDeviceConnection
        ↓ getFileDescriptor() 交给 native
C/C++ (NDK)：libusb 用该 fd 打开 → libusb_fill_iso_transfer 做等时传输
        （或自己写 usbfs ioctl URB_ISOCHRONOUS）
```

**附带影响**：libusb 的等时传输是**异步回调**模型，与现有「同步写缓冲」的 WASAPI 风格差异大，
**发送缓冲策略必须重写**（与 AAudio 那条「回调驱动」的结论是同一类问题）。
**不需要 root**（UAPP / Vox Machina 已证明这条路可行）。

### 3.3 与 RTANet 的关系（用户 2026-10-27 判断）

> 用户原话：「其实这也是我们 RLNet 可以用起来的唯一路径」

**判断正确**：RTANet 当年冻结的真因（`docs\RTANet-冻结说明.md:41`）是
**「几乎没有数播能安装我们的协议」** —— 这是**硬件生态**问题。

而 **UAC2 不用说服任何硬件厂**：DAC 出厂就符合 USB 标准。
⟹ 手机 + 我们自研 UAC2 栈 = **RTANet 的第一个真实部署场景**。

⚠️ **命名澄清**：仓库里**没有任何 `RLNet` 标识**（grep 0 命中），
协议名是 **RTANet**（`src/net/rtanet.h`，`tools/rtanet_rx.exe`）。用户说的「RLNet」应即 RTANet，
**落盘时以 RTANet 为准**；如确指另一协议，需用户另行确认。

可能的演进形态（待用户定夺）：
- 形态 A：手机端 = 完整播放器（DSP + UAC2），RTANet 仍用于 **PC → 手机** 的数据分发。
- 形态 B：手机端 = **端点**，接收 RTANet 流再 UAC2 输出（把 RTANet 的「端点机」角色由手机承担）。
- 两者可并存，但**先做形态 B 的成本最低**——因为它把「DSP 在手机上跑」这个最难的算力问题暂时绕开。

## 4. 升频强度：静态表 + 运行时校准

### 4.1 为什么必须两层

| 层 | 内容 | 为什么 |
|---|---|---|
| **静态表** | 按 SoC 预置保守默认（高通旗舰一年一代，5 年只有 5~6 个型号，**可人工维护**） | 手机 CPU 型号确实不多（用户判断正确） |
| **运行时校准** | 首次接 DAC 跑 2~3 秒真实 kernel，测实际耗时，自动升/降档 | 降频曲线、ALU 利用率、浮点行为**算不出来，只能测** |

### 4.2 「最佳适配」的定义（主动选择，不是被动妥协）

> **在过渡带 ≥ 21 kHz 的硬底线前提下，选能稳定跑满的最长抽头。**

理由：过渡带低于 21 kHz 是**可闻劣化**（见 §4.3），而抽头再长只是「更接近理想」，两者不对称。

### 4.3 抽头长度的实际影响（用户问过，结论存档）

| 抽头 | 过渡带（44.1k 源） | 结论 |
|---|---|---|
| 262144（sinc-M 级） | ±5 Hz | PC 端用 |
| 65536（poly-sinc-long） | ±20 Hz | 手机可接受 |
| **16384（poly-sinc-short）** | **±80 Hz** | **手机安全底线**（仍在 21 kHz 以上） |
| 4096 | ±320 Hz | ❌ 过渡带下探到 19.5 kHz，**会产生可闻高频锯齿** |

阻带：180 dB → 短抽头约 140~150 dB，**仍远超 `docs\音质极限分析.md` 自定的「−120 dB 以下无意义」**。

### 4.4 8 Gen 2 可行性估算

Adreno 740 = **2.09 TFLOPS fp32 峰值**（1536 ALU × 680 MHz × 2），
持续负载实测约 **70%**（Xataka 实测 8 Gen 2 持续降幅约 67.9%）:

| 配置 | 结论 |
|---|---|
| ×16 + 262144 抽头 + 模拟 double | ❌ 跑不动 |
| ×16 + 65536 抽头 + 模拟 double | ✅ 余量充足 |
| ×16 + 16384 抽头 + 模拟 double | ✅ 轻松 |

### 4.5 「降档」的陷阱（用户问过）

**不能只靠降输出采样率省算力**：降到 176.4k 确实省 3/4 算力，
但 **DAC 内部的廉价插值滤波器会接手剩下的工作** —— 与做升频的初衷矛盾。
⟹ 正确做法：**保持 705.6k 输出 + 缩短每级抽头**。

## 5. ARM 适用范围（用户问过）

| 项 | 结论 |
|---|---|
| **CPU 侧** | **ARMv8 全系适用**。float64 与 NEON 在 ARMv8 都是**强制要求**，不像 x86 需区分 AVX 版本；只要 `-ffp-contract=off` 且无 reassoc，double 结果与 x86 **按 IEEE-754 是同一个值** |
| **GPU 侧** | Adreno 730（8 Gen 1，1.84T）起可用；740（8 Gen 2，2.09T）有安全余量；750/830 更宽裕。6xx 老中端需大幅降档 |
| **fp64** | **移动 Adreno 全系没有 fp64** —— 这是**移动 GPU 行业共性**（Apple / Mali 同样），不是高通缺陷。所以必须走 float2 模拟 |
| **GPU 后端** | 放弃 HIP/CUDA，改 **OpenCL**。`gpu_bridge.h` 的「动态加载、失败自动退回 CPU」设计**原样可搬**（`LoadLibrary` → `dlopen`） |

## 8. 明确不做的（写下来免得反复讨论）

| 想法 | 为什么不 |
|---|---|
| AAudio 当主路径 | 过系统混音器与 HAL 重采样，**无法保证 bit-perfect** |
| 直接用 float32 算升频 | **信息论上装不下**（§2.2），无论怎么写 kernel |
| 追求「逐位」但只测 max|Δ| 一个数 | 判据不充分（铁律 3），必须测**误差频谱与自相关**，确认误差不是结构性的 |
| 只靠降输出采样率省算力 | DAC 廉价滤波器会补回（§4.5） |
| Vulkan Compute 当主路 | 驱动质量参差（社区实测 8 Elite 的量化管线是坏的），只作备选 |
