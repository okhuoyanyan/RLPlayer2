## 2. 第 6a 条：封面

### 2.1 统计（真实库 655 首）

| 级别 | 有封面 | 无封面 | 覆盖率 |
|---|---|---|---|
| 曲目 | 303 | 352 | 46.3% |
| 专辑（173） | 112 | 61 | 64.7% |
| 艺术家（246） | **101** | **145** | **41.1%**（其余 58.9% 只能显示首字母） |

按格式：`.flac` 248/572、`.wav` 43/71、`.mp3` 10/10、`.ogg` 1/1、`.dsf` 1/1。

### 2.2 「文件里真没有」还是「解析漏了」？—— 解析没错

- `hasCover` 定义：内嵌封面流 **或** 同目录 `cover/folder/front.{jpg,jpeg,png}`（`library.h:726`）。
- **A/B（173 首，87 个目录，每目录 ≤2 首，逐首 ffprobe）**：索引=1&真=1 共 67，索引=1&真=0 **0**，
  索引=0&真=1 **0**，索引=0&真=0 共 106 ⟹ **零误报零漏报**。
- **无封面抽样 24 例**（跨 24 个目录，全部 `.flac`/`.wav`）：`streams=1 audio=1 video=0`，
  且无同目录封面文件 ⟹ **24/24 文件里真的没有图**。

### 2.3 真 bug：`albumCover` 只问「首曲」，且把 1x1 占位图当封面缓存起来

`src/audio/media_info.h:365-375`：`get_cover()` 找不到封面时**不返回空**，而是返回一张
**1x1 透明 PNG**（约 77~200 字节）。而 `library.h:1088` 旧实现只取 `tracks_[a.idx[0]].path` 问一次，
结果又被写进 `coverCache_` **永不重试**。后果：`cv:true` 的专辑里，只要首曲没图，整张就是空白，
`<img onerror>` 也兜不住（HTTP 200 + 合法 PNG）。

实测受影响专辑：**2 张**（`Inoch EP Revisited`、`春秋歷命序`）—— 首曲 cv=0，但专辑里有 cv=1 的曲目。
数量不大，但它同时解释了**艺术家头像**的随机性（见 §3）。

### 2.4 已修的改动（`src/net/library.h:1078-1141`）

```
1) 取图顺序改为「本专辑 cv=1 的曲目优先（≤3 首），再其余曲目（≤3 首）」，不再只看 idx[0]；
2) 拿到的图 < 1 KB 视为占位，继续试下一首；全部试完仍只有小图才用它；
3) 空/占位结果写**负缓存**并返回 false（让 onerror 露回首字母），不再把占位图当封面缓存。
```

**实测（真库 + 真 HTTP，实例 8932）**：`/api/lib/albums` 报 `cv=true` 的 **124** 张专辑逐个拉
`/api/lib/cover?k=` ⟹ **真封面 124 / 占位 0 / 错误 0**。
（修改前这 2 张会给 1x1 占位图。）

### 2.5 仍然缺的（不是 bug，是没数据）

352 首 / 61 张专辑 / 145 位艺术家**确实没有任何图源**。要补只能接外部元数据（`/api/enrich`、
QQ/网易/iTunes 已实现），**不在本次可改范围**（属于 `src/meta/provider.h`，且是功能而非缺陷）。

## 4. 第 6c 条：曲名「？？？？？？」

### 4.1 先排除：不是索引损坏

### 4.2 原因①：16 首 WAV 的标签**本身就是字面问号**（已修）

逐字节取证（`人声音质（女高音） - たいせつなきみのために…(Live).wav`）：
- RIFF `LIST/INFO` 的 `INAM` = **33 字节**：`3F 3F 3F … 3F 20 28 4C 69 76 65 29` = `"????????????????????????? (Live)"`
- 同文件尾部 `id3 ` 块的 `TIT2`（enc=1 UTF-16LE）= `"たいせつなきみのために、ぼくにできるいちばんのこと (Live)"`

`ffprobe -of default=nw=0` 对这批文件打出**两条 TITLE**：先 FFI（坏），后 ID3（好）。
而 `lib_probe_one` 的 `put()` 是「先到先得」（`library.h:684-686`），⟹ **稳定地选中坏的那条**。
按相同结构修好之前，16/16 全部取到 `?`。

**修复**（`src/meta/tags_native.h:593-650`）：新增 `tag_is_placeholder()`，
在 WAV 跨块合并 `TagMerger::absorb` 里把「去掉数字与空白后全是 `?`（含全角 `？`）且至少有一个 `?`」
的值判成空，于是 ID3 那条好标签得以占位。

**实测（真库 71 个 WAV 重新扫描，本机已装 clang 构建 `build-fb02c`）**：

| 结果 | 数量 | 例 |
|---|---|---|
| 修好 | **6** | `???`→`不由己`；`??????`→`威廉退尔序曲`；`??????`→`天空の悲恋歌`；`????`→`いのち。`；`??`→`孤独`（×2） |
| 仍坏 | 10 | 见下 |

全部 655 行索引 diff：**只有这 6 行的 title 变了**，其余列一字节未动 ⟹ 无回归。

**剩余 10 首为什么修不了**：这些文件的坏标签是**混合**的（`Kokoro no Ame ~???~`、
`????? (Chinese Tea)`、`J. Strauss II - …(?????????,??326)`）。判据「纯占位」不会命中，
因为在「干净版本」里这些 `?` 本来就在句子中间；它们**同时**出现在文件名里，说明是**下游工具（转码/重命名）
写盘时就坏了**，ID3 里是否还有干净值要对每个文件单独判定。当前策略是**不猜**（铁律：宁可留 `?`，不给错名）。

**⚠️ 未解决（如实记录）**：10/16 的 title 仍是 `?`。若要继续，需要一条更强的判据：
「同键两个来源里，若 A 含 `?` 而 B 不含且长度接近，取 B」。风险是改名（假阳），故本次**不做**，
建议先对真实库做一次「人工确认 10 例」再决定。

### 4.3 原因②：UI 首选字体 **Segoe UI 没有 CJK 字形**（字体结论）

字体链（`src/net/ui_page.h:72`）：
```
body{font:13px/1.5 Inter,'Segoe UI Variable','Segoe UI',system-ui,sans-serif}
```
本机档案（`C:\Windows\Fonts`）：**Inter 未安装**；`SegUIVar.ttf`（Segoe UI Variable）、
`segoeui.ttf`（Segoe UI）在。

**逐字符 cmap 实证**（方法见下，脚本 `build-fb02c_tmp/cmap_check*.py`）：

| 字符 | Segoe UI Variable | Segoe UI | 微软雅黑 | Yu Gothic | Noto Sans SC |
|---|---|---|---|---|---|
| `銀` U+9280 | **无** | **无** | 有 | 有 | 有 |
| `龍` U+9F8D | **无** | **无** | 有 | 有 | 有 |
| `の` U+306E | **无** | **无** | 有 | 有 | 有 |
| `?` U+003F | 有 | 有 | 有 | 有 | 有 |
| `？` U+FF1F | **无** | **无** | 有 | 有 | 有 |

整串 `銀の龍の背に乗って`（9 字）：**Segoe UI Variable 9/9 全部 MISSING**，微软雅黑 9/9 OK。
Segoe UI 只有 **2417 / 3998** 个码位（纯拉丁+符号），**一个 CJK 都没有**。

⟹ 中文/日文曲名**必须**靠 Chromium 的系统字体回退（本机 572 个字体面，能兜住）。
一旦回退失败或落到无 CJK 的字体上，缺字形就会渲染成 `?` 或豆腐块 —— 这正是「字体」这一路的证据。

**给主控立即可做的一行修（UI 线，未改）**：把 CJK 显式写进字体链首位，不再依赖回退：
```
font:13px/1.5 'Microsoft YaHei UI','Microsoft YaHei','PingFang SC','Noto Sans CJK SC','Yu Gothic UI',
     Inter,'Segoe UI Variable','Segoe UI',system-ui,sans-serif
```
同时给 `body` 加 `font-feature-settings:'locl'` 不必；但建议加
`html{text-rendering:optimizeLegibility}` 之外**不要**开 `font-synthesis` 之类的开关。

**「逐字符查 cmap」的可复现实证方法**（本机 Python 3.13，无 fontTools 依赖，纯 struct 解析）：
1. 读 `.ttf`/`.ttc` 的 table directory（`.ttc` 要按 `ttcf` 头的偏移表逐个 face）；
2. 找 `cmap` 表，遍历所有 (platformID, encodingID) 子表，只认 **format 4 / 12**；
3. format 4：读 `endCode[]`/`startCode[]`/`idDelta[]`/`idRangeOffset[]`，对目标码位做
   `g = (c + idDelta) & 0xFFFF`（或 glyphIdArray 查表），`g != 0` 即「有字形」；
   format 12：按 group `startCharCode..endCharCode` 区间判定；
4. **注意坑**：雅黑/宋体这类中文 `.ttc` 的 `cmap` 里有大量非 4/12 的子表，
   且子表偏移要从**整个 cmap 表头**起算 —— 只解析「第一个子表」会得到 0 个字形的假阴性
   （本次第一版脚本就踩了，已修正）。
5. 判据：**同一首歌的标题逐字符**查 `font-family` 链上**每一个**字体，
   只要链上首个命中的字体对所有字符都返回 true，就不会出现 `?`。
