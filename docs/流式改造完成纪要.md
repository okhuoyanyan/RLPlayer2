## 2. 本轮做的：卷积器 FIFO

均匀分块 FFT 卷积要求固定块长，无法直接接受任意分块。新加的 StreamingConvolver：

- 输入进 FIFO，攒满 B 个才交一块给 PartitionedConvolver
- **输出 FIFO 预置 B 个零** —— 代表 B 帧算法延迟
- 每次调用弹出与输入等量的输出

于是「整块喂」与「分块喂」产生完全相同的输出序列（同样延迟 B 帧）。

代价：B 帧延迟。convBlock 默认 1024，@44.1k 约 23 ms —— 对动辄数十万抽头的房间校正可忽略。

## 3. 本轮踩的两个坑

**坑 1：vector<unique_ptr<T>> 不能用 assign(n, nullptr)**
它要求元素可拷贝，而 unique_ptr 不可拷贝。改用 resize(n)。

**坑 2：GPU 路径没有延迟，不能和 CPU 路径共用同一个比对偏移**
最初把测试统一按 convBlock 延迟比对，结果只有 GPU 用例失败。
正确做法是按**实际走的路径**取延迟：

    const size_t lat2 = st.usedGpuConvolution ? 0 : cfg.convBlock;

GPU 是整块卷积（无 FIFO 状态），CPU 是流式卷积器（有 convBlock 延迟）。两者语义不同，
比对方式也必须不同。

## 4. 现在解锁了什么

- **低延迟起播**：可以边解码边处理，不必把整个文件读进内存
- **网络流式接收**：RTANet 分块到达的数据可以直接进管线
- **Web 实时进度**：有了流式管线，状态可以反映播放进度而非启动快照

## 5. 已知边界

- **GPU 卷积路径不是流式的**（整块卷积、无跨调用状态）。当前只在显式 useGpu 时走，
  且需要调用方一次喂完整缓冲。若日后要让 GPU 也流式化，需要把环形历史搬到 GPU。
- convBlock 延迟会叠加到端到端延迟上（23 ms 量级）。
