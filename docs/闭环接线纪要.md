# 闭环接入真实收发路径纪要（Round 22）

代码：[tools/rtanet_rx.cpp](tools/rtanet_rx.cpp)（端点回传）、[tools/rtaplay.cpp](tools/rtaplay.cpp)（发送端消费）

## 1. 接线内容

```
端点 rtanet_rx                          发送端 rtaplay --net
  ├ 每包到达时喂 DriftEstimator          ├ 每次等待间隙读控制面（非阻塞）
  ├ 每 100 ms 写一行 STATUS ──────────>  ├ parse_status()
  │                                       ├ ClockLoop::update()
  │                                       └ applied 修正 → 调整发送节奏
  └ 复用 Round 12 建立的控制面 TCP 连接
```

发送端的修正作用在「每帧允许的真实时长」上：
```cpp
const double audioSec = sent / (rate * (1.0 + applied * 1e-6));
```
加快即允许更短时间，等效于异步重采样的速率提升。

## 2. 真实程序端到端实测

```
rtaplay loop_src.wav --net 127.0.0.1:45993      (8 秒 / 44.1k / 24bit)
        ↓ 2757 包
rtanet_rx --sink file --out loop_rx.wav

闭环: 收到 73 条状态回传 | 末次水位 0.0 ms | 末次漂移 +291.6 ppm | 最终修正 +105.8 ppm
逐位比对: 2116800 字节 / 705600 样本 —— ✅ 逐位完全相同
```

**73 条回传 / 8 秒 ≈ 每 110 ms 一条**，与 100 ms 的设计一致。

**最关键的一点：加了闭环之后逐位完美性没有被破坏** —— 状态回传走的是独立的 TCP 控制面，
不占用也不改动 UDP 数据面的任何一个样本。这是这个架构的价值所在。

## 3. 观察到的现象（供后续调优参考）

- 末次漂移 +291.6 ppm 明显大于真实晶振漂移量级（通常 ±100 ppm 以内）——
  因为回环上的包到达时间受发送端自身节奏影响，估计里混入了发送端的调整动作。
  Round 20 的「扣除自身修正」在控制环内做了，但**端点侧的估计器**没有扣除，
  所以回传给发送端的 drift 本身偏大。**这是下一步要修的点。**
- 尽管如此，水位被控制在 0.0 ms（端点刚交付完），没有溢出或断流。
