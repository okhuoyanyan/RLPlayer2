# 流式改造基线纪要（Round 32）

测试：tests/test_stream_baseline.cpp

## 1. 为什么先做这个

「管线改流式分块」是当前架构上唯一的关键短板（Web 实时状态、低延迟起播都卡在它）。
但动手之前必须先有**客观基线**：一来说明改造到底要解决什么，二来给出必须超越的判据。

## 2. 基线数据（这是一个真缺陷，不是形式）

输入 24000 帧 @48kHz 24-bit 立体声，比较「整块处理」与「切 4096 帧分块处理」的输出：

| 路径 | 差异样本 | 占比 |
|---|---|---|
| 直通（无状态） | **0** | 0% |
| **升频（2x）** | **68164 / 96000** | **71.0%** |
| EQ | 3276 / 48000 | 6.8% |
| 卷积 | 5110 / 48000 | 10.6% |

**根因**：Pipeline::process() 每次调用都重建全部 DSP 对象，于是双二阶状态、
重采样器的相位累加器、抖动缓冲历史、音量渐变、延迟线——全部在分块边界被清零。

**为什么升频最严重**：重采样器的 outIdx_ 每次从 0 开始，相位图案在每个边界重新开始，
产生相位不连续。这不是轻微误差，而是 71% 的样本都不同。

## 3. 这意味着什么

**当前实现只能用于一次性整块处理整个文件**（离线转换、--analyze、以及把整个文件读进内存再输出）。

对真实播放器的常见场景都不可用：

- 边解码边播放（需要低延迟起播）
- 网络流式接收（包是分块到达的）
- Web 实时进度显示

## 4. 改造的验收判据（已固化进测试）

> **同一输入，任意分块方式，输出必须逐位一致。**

这是硬判据，不是大致接近。改造后 test_stream_baseline 必须全部为 0 差异。

## 5. 改造方案（下一步）

把 DSP 对象从「每次调用新建」改为「Pipeline 持有的持久状态」：

| 对象 | 现状 | 改造 |
|---|---|---|
| PolyphaseResampler | 每次新建（相位归零） | 持有为成员 |
| Biquad 级联 | 每次拷贝+reset | 持有为成员 |
| PartitionedConvolver | 每次新建（环形历史丢失） | 持有为成员 |
| DelayLine | 每次新建 | 持有为成员 |
| VolumeControl | 每次新建（渐变重启） | 持有为成员 |
| Quantizer | 每次新建（整形误差历史丢失） | 持有为成员 |

技术上不复杂（主要是把构造从 process() 内搬到 prepare()），但涉及面广，
所以**必须先有基线和判据**——也就是本轮做的事。

## 6. 本轮可以确认的

- 直通路径与分块完全无关（**0 差异**）—— 比特完美的核心主张不受影响
- 有状态路径的分块依赖已被精确量化，不是猜测
- 改造的验收判据已固化，改造后可直接回归
