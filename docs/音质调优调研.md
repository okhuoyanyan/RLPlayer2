> 调研日期：2026-10-20

> ＋ 中文社区（耳机大家坛 erji.net、耳机俱乐部、Chiphell、PTT）
> 证据分级：**A** 可测量或权威文档 ｜ **B** 机制清楚且社区可复现 ｜ **C** 只有主观听感、无对照 ｜ **D** 与已知物理矛盾（玄学）

## 0. 一页结论

三句话：

1. **数字域里没有"时钟"。** DSP 只是对一堆数字做数学运算，时钟只在最后的 D/A 转换才出现。因此"CPU 频率 / 内存速度 / 定时器精度 改变了音质"这类说法，若输出比特完全相同，物理上只剩下一条通路：**电气耦合**（地环路、RF 泄漏、供电扰动）影响 DAC 的模拟部分。凡不能落到这条通路上的说法，都是玄学。
2. **真正能改变"听到的声音"的只有四件事**：滤波器/调制器的选择、输出采样率、增益结构（含 inter-sample over）、以及"不出丢样/爆音"。系统调优（MMCSS、定时器、优先级、亲和性、DPC）只影响第 4 件事——**它决定"会不会翻车"，不决定"翻车之外的声音"**。
3. 对照我们的现状：**能落地的增量集中在"可观测性"和"增益/滤波结构"**，而不是继续加系统调优。定时器、MMCSS、线程优先级、独占事件驱动、整曲预解码都已经做了，再往上加属于边际递减。

## 1. 证据分级与"能证明什么"的判据

本项目的铁律之一是「测试通过 ≠ 测对了东西」，所以先把判据写死：

| 判据 | 能证明 | 不能证明 |
|---|---|---|
| **比特比对 / null test**（两路相减，残差 −∞） | 输出完全一致 | 模拟端是否一致（电气差异仍在） |
| **频谱 / 冲激响应 / 群延迟** | 滤波器确实变了 | 人耳是否听得出 |
| **欠载与丢样计数**（事件超时、写入 0 帧、pad 异常） | 链路是否翻车 | 翻车之外的声音差异 |
| **DPC/ISR 时间**（LatencyMon） | 系统能否在周期内响应 | 声音好坏 |
| **ABX（电平匹配、无缝切换、≥10 次）** | 可听差异是否存在 | 差异有多大、是否"更好" |
| **仅主观描述（"线条更清楚""更厚"）** | 说话人的感受 | 任何客观事实 |

统计门槛：10 次 ABX 中答对 ≥9 次，p ≈ 0.011（二项分布），才算"有可听差异"。这是最低门槛，不是金标准。

> 本项目播放纪律：任何验证都不需要听得见。测试信号一律 ≤ −60 dBFS；优先 --analyze 离线跑管线；确需真实播放时先报设备名、时长、峰值电平。

## 2. 逐项调研

### 2.1 Jussi Laako（HQPlayer 作者）到底说过什么

**结论**：他在 Roon 官方论坛（HQPlayer 的官方支持场所，日均回帖）与 Audiophile Style 上的立场高度一致，可归纳为五条：

| 他的原话要点 | 出处 | 等级 |
|---|---|---|
| **DSP 里没有时钟**："There is no clock involved in the DSP calculations… Clock is only applied at the very final stage, when the values are converted to analog form." | Roon 社区 [p/1538510](https://community.roonlabs.com/p/1538510) | A |
| **USB 重整（reclock）无意义**："Since the USB clock is not used for audio. And master clock responsible for clocking audio is owned by the DAC, I don't see any benefit in reclocking USB… These clocks have no relation to audio clocks, they just facilitate data transfer between two RAM buffers." | [p/1137671](https://community.roonlabs.com/p/1137671) | A |
| **真正决定输出质量的是 dither / noise-shaper**："What matters for the output quality is dither/noise-shaper used for the output data… every increase in sampling rate will drop the audio band noise floor." | [p/1475466](https://community.roonlabs.com/p/1475466) | A |
| **不要去动系统优先级**："So generally, don't mess with these. HQPlayer already assigns carefully designed process and thread priorities… even idle priority thread of real-time class would starve normal class time-critical thread… In worst case, you risk having your system deadlock." | [p/1543070](https://community.roonlabs.com/p/1543070) | A |
| **模拟线材可能有用，数字线材/网络"净化器"没用**；真正的问题是**屏蔽层噪声与地环路**：用带屏蔽的网线反而破坏以太网变压器提供的隔离。 | [p/1189551](https://community.roonlabs.com/p/1189551)、[p/1952275](https://community.roonlabs.com/p/1952275) | A |

他对"什么不影响音质"的隐含判断也很明确：

- **CPU 快慢只决定"跑不跑得动"**：他在多处把 CPU/内存带宽/GPU 讨论限定在"能否实时跑某个调制器/滤波器"（例如 5 GHz 才够 DSD1024 的 ASDM7EC），从不主张"更快的 CPU 声音更好"。
- **DAC 内部 PLL 开/关是可测的**："This will increase the amount of jitter in the DAC output by some orders of magnitude (some tens of dB)."——注意，这里说的是 **DAC 内部**的 PLL，不是 PC 侧。([p/2057224](https://community.roonlabs.com/p/2057224))

**我们能不能实现**：观点不能"实现"，但可以转成设计原则：
- 别再优化"数字域时序"，去优化"比特正确的滤波/抖动链"；
- 系统层只保留"防翻车"的最低限度（我们已达成）；
- 若将来做 USB/网络输出，优先做**电气隔离**（光纤以太网、NAA 式分离），而不是"重整时钟"。

**实现代价**：0（是取舍，不是代码）。

### 2.2 CPU 频率 / 核心隔离 / C-State / SpeedStep 有没有可测影响

**结论**：**对"比特与音质"没有证据；对"会不会爆音"有机制、有零散实证。**

- 输出比特与 CPU 频率无关（数学运算的结果不依赖算得多快）。
- 可测的影响只有一种：**实时线程能否在周期内被调度到**。当缓冲小（3–10 ms）且系统有高 DPC 负载时，频率过低/核心被占用/深 C-State 唤醒延迟都会造成**欠载=爆音**。
- "核心隔离"（把播放线程钉在某个核）在 Windows 上**收益不确定，甚至可能有害**：被钉的核若同时承担 USB/音频中断，反而更糟；跨核迁移的 L1/L2 失效代价（几十微秒）通常远小于一次欠载窗口。
- 真正有实证的是 **P/E 核（大小核）调度**：DAW 用户报告在 12 代以后 Intel 上，E-core 抢占导致实时音频爆音，禁用 E-core 或指定 P-core 后消失（[Steinberg WaveLab 帖](https://forums.steinberg.net/t/wavelab-and-intel-p-cores-and-e-cores-my-experience-and-solution/974790)）。这是"调度正确性"问题，不是"音质"问题。
- **BIOS 变频 / SpeedStep / Cool'n'Quiet**：老牌 DAW 建议关掉它们，理由是"基准测试计时不准"和"唤醒延迟"。对播放而言，C-State 退出延迟在**数十到上百微秒**量级，相对于 3 ms 周期仍有 1–2 个数量级余量；只有在"极小缓冲 + 高负载 + 深睡眠"的边缘工况才会显形。
- **Windows 的"内核隔离/内存完整性"（VBS/HVCI）**：这是安全功能，实测会带来可观性能损失（游戏场景常见 5–30%），虚拟化层也可能抬高 DPC 延迟；但**没有任何证据显示它会改变模拟输出的声音**。开启它属于安全 vs 性能取舍，不是音质取舍。
- 中文社区的"Process Lasso 十分钟打造准 HiFi 电脑"（[erji.net](http://www2.erji.net/forum.php?mod=viewthread&action=printable&tid=2399686)）属于把"减少爆音概率"包装成"提升音质"，无对照实验，等级 C。

**证据**：
- 机制与阈值：LatencyMon 官方判定（DPC/ISR < 2000 µs 合格，2000–4000 µs 可疑，> 4000 µs 不合格）——[resplendence.com](https://resplendence.com/latencymon_using)。
- 大小核实证：Steinberg 论坛（同上），等级 B。
- VBS 性能影响：[mezha.ua 报道](https://mezha.ua/en/news/windows-11-memory-integrity-314776/)，等级 B（性能），与音质无关。

**我们能不能实现**：
- 已做：单核亲和（硬编码 core 2）+ TIME_CRITICAL + MMCSS。
- 可做且值得做：**亲和性 A/B**（不绑 / 绑 core2 / 绑到"中断不落在这个核"的核），判据用我们自己的欠载计数器 + LatencyMon 的 per-CPU 视图，而不是耳朵。
- 不建议：改 BIOS 变频、关 C-State、关 VBS（收益不可测，代价明确）。

**实现代价**：A/B 实验约 0.5 天；改 BIOS 为零代码但要重启机器，且不可回滚验证。

### 2.3 GPU 频率对音频（尤其 GPU 卷积）有没有影响；显存/ASPM 会不会卡顿

**结论**：**GPU 频率不改变卷积结果的比特**；会改变的是"能否在截止时间前算完"和"PCIe 链路状态会不会拖慢其它设备"。

- 我们的卷积是确定性算法，频率只影响耗时（现状：262144 抽头、1 秒音频 2.0 ms，余量三个数量级）。**只要不超时，频率对声音零影响**。
- 真正的风险是三类"非计算"问题：
  1. **驱动 DPC**：显卡驱动（nvlddmkm / AMD 的 display+audio 驱动）DPC 尖峰可以到毫秒级，挤压音频线程。中文技术文与 LatencyMon 案例里这都是头号嫌疑（[php.cn 案例](https://www.php.cn/faq/2683005.html)，等级 C；但机制与 ASR/厂商论坛一致）。
  2. **PCIe ASPM / L1 子状态**：链路进入低功耗后，事务要"唤醒"链路，引入微秒级固定延迟；xHCI（USB 控制器）与显卡常挂在同一颗芯片组的链路上，因此**显卡的电源管理会波及 USB 音频**。实证：ASUS ROG 论坛"RTX 5060 Ti + ASPM 导致严重 DPC 延迟"（[链接](https://rog-forum.asus.com/t5/gaming-motherboards/severe-dpc-latency-aspm-instability-with-rtx-5060-ti-on-rog/td-p/1165485)）；Chiphell 中文帖"开 ASPM 影响 SSD 的 4K，声卡还容易爆音"（[链接](https://www.chiphell.com/archiver/tid-2658928.html)）。等级 B。
  3. **低功耗状态切换本身**：**同型号 GPU** 的实证——RX 9070 XT 在 5–10 W 超低功耗下经 DisplayPort 输出会"popping"（[CachyOS 论坛](https://discuss.cachyos.org/t/audio-popping-on-rx-9070-xt-via-displayport-at-ultra-low-power-5w-10w/35284)）；AMD 官方论坛也有 9070 XT HDMI 音频在 idle 时爆音的帖子（[链接](https://pcforum.amd.com/s/question/0D5KZ00000sFPnF0AW/9070-xt-hdmi-audio-output-is-producing-noise-artifacts-sputtering-crackling-popping-noises-while-idle-seeking-a-driver-update-to-correct)）。注意：那是**显卡自带音频**，我们走 USB DAC 时机制不同，但它证明"GPU 电源状态切换会耦合进音频"。
- **显存**：与音质无关；只有在显存不足导致 WDDM 驱逐/分页时才会造成毫秒级停顿。

**证据等级**：B（机制实证 + 同型号案例；本机未受控测量）。

**我们能不能实现**：
- **GPU 看门狗**：每块卷积计时，超阈值（例如 > 该块播放时长的 20%）就降到 CPU 或加深队列，并记账。这是"防翻车"，可落地。
- **预热**：起播前跑一次平凡卷积（写常数 kernel），把 GPU 从低功耗态拉起来，避免第一块超时。注意本项目铁律 5：kernel 必须 --offload-arch=gfx1201，且要用平凡 kernel 验证真的执行了。
- **不建议**程序去改 ASPM（BIOS/注册表级，风险高）；写成**检查清单**让用户自己决定。

**实现代价**：看门狗 + 预热约 1 天；检测 ASPM 状态约 1–2 天（SetupAPI/注册表），只读。

### 2.4 WASAPI 独占：事件驱动 vs 推送；缓冲大小与周期的真实影响

**结论**：**两种模式输出的比特完全相同**，差别只在"谁来定时"和"翻车方式"。

| 维度 | 事件驱动（EVENTCALLBACK） | 推送（polling） |
|---|---|---|
| 节奏来源 | 驱动在周期边界置事件 | 应用自己 Sleep/自旋，按 GetCurrentPadding 估计 |
| 时间精度依赖 | 不依赖定时器精度 | 依赖 Sleep 粒度（历史上 15.6 ms，故有 timeBeginPeriod） |
| 典型故障 | 事件没被及时响应 → 驱动停发事件（本机 Round 6 实测：直接静音） | Sleep 过头 → 欠载爆音 |
| 比特 | 一致 | 一致 |

- Microsoft 的官方低延迟配方就是：**独占 + AUDCLNT_STREAMFLAGS_EVENTCALLBACK + MMCSS**（[Exclusive-Mode Streams](https://learn.microsoft.com/en-us/windows/win32/coreaudio/exclusive-mode-streams)）。Win10 起还多了 IAudioClient3 的"共享模式低周期"路线，可做到接近独占的延迟而保留混音。
- **缓冲与周期**：独占模式下缓冲时长同时决定**延迟**和**抗调度抖动余量**。本机实测（X8）：hnsPeriodicity 必须等于 hnsBufferDuration（传 0 直接 AUDCLNT_E_BUFFER_SIZE_ERROR），即"缓冲 = 一个周期"；设备默认周期 10 ms、最小 3 ms；100/50/20/10/3 ms 全部可开流。驱动是否允许 N>1 个周期取决于厂商，不能一概而论。
- Jussi 对缓冲的表述可作为工程共识：**"Buffer time" 是硬件 DMA 缓冲**，"Short buffer" 是软件 FIFO；把两者都压到最小会让系统"对 drop-out 敏感"（[p/1927195](https://community.roonlabs.com/p/1927195)、[p/2197154](https://community.roonlabs.com/p/2197154)）。他还建议把 ASIO 缓冲"开到最大"以免一点系统活动就爆音（[p/1950454](https://community.roonlabs.com/p/1950454)）。
- 中文社区流传"event 线条更明显、push 更厚、ASIO 最尖"（[耳机俱乐部](http://www.headphoneclub.com/forum.php?mod=viewthread&tid=361331)）——三种模式在独占下写入的是同一串样本，**等级 D**。真正可能造成差异的是：不同路径下驱动内部缓冲/时钟域不同、或某一路其实没走独占。

**证据等级**：A（Microsoft 官方文档 + 本机实测）；中文社区「event 更线条、push 更厚」为 D。

**我们能不能实现**：
- 已做：独占 + 事件 + GetCurrentPadding 驱动写入（pump_consumed）。
- **仍有一处脆弱**：rtaweb 路径用 write_one_period，要求 pad == 0 才写，否则整周期丢弃（返回 0）。在"真实周期短于请求周期"的设备上（P1 纪要里的 14.8% 异常）这会退化为周期性空转。
- 可做：**周期/缓冲双档位**（低延迟 3–10 ms / 抗抖动 50–100 ms）＋每档记录欠载率，让"缓冲多大"由数据决定，而不是由听感决定。

**实现代价**：档位与统计约 0.5 天；修 pad==0 的脆弱逻辑约 0.5 天。

### 2.5 定时器精度 / MMCSS / 线程优先级 / 亲和性的真实效果

**结论**：这四项只影响**调度及时性**，不影响音色；且**我们已经全做了**，继续加码的边际收益接近零，甚至有反作用。

- **timeBeginPeriod**：Windows 10 2004 起规则变了——一个进程调 timeBeginPeriod **不再显著影响其它进程**，系统不再被单个程序"拖到 1 ms 节拍"（Bruce Dawson 的实测与分析：[Windows Timer Resolution: The Great Rule Change](https://randomascii.wordpress.com/2020/10/04/windows-timer-resolution-the-great-rule-change/)）。也就是说：**我们调 timeBeginPeriod(1) 主要只让自己进程的 Sleep 更细**，对驱动/其它进程基本无影响。而事件驱动模式本来就不靠定时器，所以它的实际价值集中在"我们自己 Sleep 的地方"。
- **MMCSS**：注册表里的 Pro Audio 任务，给线程更高的调度权且不被后台任务抢占（[MS 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)）。微软音频团队 Matthew van Eerde 在 wdmaudiodev 邮件列表里对"应用是否需要自己提优先级"的回答是：**"No, MMCSS should suffice"**（[原帖](https://www.freelists.org/post/wdmaudiodev/WASAPI-exclusive-mode-audio-render-issue-2,1)，Cloudflare 可能拦住直连）。
- **线程优先级**：在 MMCSS 线程上再叠 TIME_CRITICAL，属于"双保险也可能是双刃剑"——Jussi 明确警告优先级错配会让系统饿死关键服务甚至死锁（[p/1543070](https://community.roonlabs.com/p/1543070)）。
- **CPU 亲和性**：绑定能减少迁移开销，但也可能把线程钉在"中断密集"的核上，或与 DSP 线程抢同一个核。**没有普适最优，只有本机测量**。
- 中文社区"foobar2000 的 MMCSS 严重劣化音质"（[erji.net](http://erji.net/forum.php?mod=viewthread&tid=2351162)）与微软文档、van Eerde 的说法直接冲突，且无对照实验，**等级 D**。

**证据等级**：A（Windows 行为与官方文档）+ D（社区听感断言）。

**我们能不能实现**：已达成（rt_tune.h：MMCSS Pro Audio + AVRT_PRIORITY_CRITICAL + TIME_CRITICAL + core 2 亲和 + timeBeginPeriod(1)；rtaweb 还设了 HIGH_PRIORITY_CLASS）。
**建议**：不要再加；改为做一次**受控 A/B**（有/无 TIME_CRITICAL；绑核/不绑核），用欠载计数判定，保留胜者。

**实现代价**：A/B 各半天。

### 2.6 内存锁定（VirtualLock / Large Pages）有没有意义

**结论**：**机制上成立，收益上接近零**，除非系统正在内存吃紧/换页。

- Windows 的 VirtualLock 有硬上限：**一个进程能锁的页数 ≈ 它的最小工作集（minimum working set）减去少量开销**；要锁更多必须先 SetProcessWorkingSetSize 抬升工作集（[MS 文档](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtuallock)）。所以"把整首歌 1.7 GB 锁进物理内存"既做不到，也不该做。
- 我们的架构已经规避了最大风险：rtaweb 是**分块流式**（队列 8 块、内存恒定在几秒量级），rtaplay 是整曲在内存但一次性顺序读。真正会被换页影响的只有：
  - 滤波器系数表（sinc-M 524287 抽头 × double ≈ 4 MB）——每首歌都要重新卷积，但一旦开始就反复读，工作集稳定；
  - 生产队列里尚未消费的几块 PCM。
- **大页（2 MB）**：需要 SeLockMemoryPrivilege（管理员 + 本地安全策略），不可分页、TLB 命中更好。对 256k 抽头卷积/FFT 可能有几个百分点的速度收益，**对声音没有可测影响**。
- 反面证据：真正影响稳定性的是内存**可靠性**而非"锁定"——Jussi 反复建议跑 24 小时 memtest86，用 ECC（[p/1331869](https://community.roonlabs.com/p/1331869)）。不稳定内存会直接导致爆音、崩溃。

**证据等级**：B（API 限制是 A 级；「锁内存提升音质」无任何可测证据）。

**我们能不能实现**：能，且很便宜。
- SetProcessWorkingSetSize(最小值抬到比如 256 MB) + VirtualLock 队列块与系数表；
- 大页单独做开关，只用于卷积系数与 FFT 缓冲，A/B 测卷积耗时。

**实现代价**：0.5 天（VirtualLock）；大页 1 天（含权限申请与回退）。

### 2.7 DPC 延迟 / MSI 中断 / USB 音频驱动的实际影响，怎么测

**结论**：这三件事**只决定"会不会爆音"**，且在"小缓冲 + 高负载"时才是主要矛盾。

- **DPC/ISR**：LatencyMon 的判定阈值是执行时间 < 2000 µs 合格、2000–4000 µs 可疑、> 4000 µs 不合格（[官方说明](https://resplendence.com/latencymon_using)）。注意它测的是**执行时间**，不是"中断到被处理"的总延迟；后者才是欠载的真正杀手。所以 LatencyMon 高不一定爆音，低也不保证不爆音——**必须和播放端计数联合判断**。
- **MSI 模式**：把设备从传统线中断改成消息信号中断，能消除"共享 IRQ 被邻居拖住"的问题。igor'sLAB 有一篇实测：显卡与音频卡共享 PCIe lane/IRQ 时出现难以复现的断音，改 MSI 后消失（[中文版](https://www.igorslab.de/zh/msi-solution-for-audio-issues-and-usb-problems/)，英文版同站 /en/）。开源工具 msi-mode-utility 也给出了改前/改后的 ISR/DPC 数据（[GitHub](https://github.com/vadyaravadim/msi-mode-utility)）。等级 B。
- **USB 音频驱动**：驱动决定"可用采样率/位深/DoP/最小周期/是否支持 native DSD"，**不改变比特**。本机 X8 只接受 24-bit PCM、不支持 88.2k 家族、min period 3 ms——这就是驱动+固件的能力边界。
- **测量工具链**：LatencyMon（DPC/ISR 排行）→ Windows Performance Recorder/xperf（深层调用栈）→ 我们自己的欠载计数（最终判据）。
- 中文资料多是"DPC 高就爆音、关硬件加速就好"的经验帖（如 [CSDN/php.cn 系列](https://adg.csdn.net/694cf0f95b9f5f31781a951e.html)），方向对但缺定量，等级 C。

**证据等级**：A（判定阈值与 API 行为）+ B（MSI 案例来自实测报告）。

**我们能不能实现**：
- 能做：**内置欠载/丢样计数器 + 事件间隔直方图**（真正的 ground truth），以及"播放期间 DPC 观察"的文档化流程。
- 不建议：程序自动改 MSI 注册表（需要管理员、可能让设备不启动）。改为**只读检测 + 提示**。

**实现代价**：计数器 1 天；MSI 只读检测 1–2 天。

### 2.8 采样率转换的滤波器设计：最小相位 vs 线性相位、apodizing、ringing、群延迟

**结论**：这是**少数几个真正改变"听到的声音"的方向**，也是 HQPlayer 的核心竞争力所在。

**物理事实（可测量）**：

| 概念 | 是什么 | 客观表现 | 主观风险 |
|---|---|---|---|
| **线性相位** | 对称 FIR，群延迟恒定 | 冲激响应关于中心对称，**瞬态前有 pre-ringing** | 预振铃在瞬态前"泄露"，理论上更易被察觉（后掩蔽强于前掩蔽） |
| **最小相位** | 能量集中在冲激响应前部 | 无 pre-ringing，**全变成 post-ringing**；相位非线性、群延迟随频率变化 | 低频相位失真；打击乐"更干净"但可能"糊" |
| **群延迟** | 线性相位滤波器的固定延迟 = (N−1)/2 个采样 | 我们 sinc-M 524287 抽头 @705.6 kHz → **约 371 ms**（0.372 s） | 只影响 A/V 同步与交互延迟，不影响音色 |
| **apodizing（切趾）** | 修改重建滤波器，让"上游 ADC 抽取滤波器留下的振铃"不再被忠实重建 | 削弱录音链路引入的 pre-ringing | 严格说不是"更准确"，是"更宽容" |
| **阻带深度** | 镜像抑制 | 16-bit 只需 96 dB；HQPlayer 顶级做到 240 dB | −120 dB 以下对听感无意义（本项目已确认过） |

- apodizing 的经典出处：Peter G. Craven, *Antialias Filters and System Transient Response at High Sample Rates*, J. Audio Eng. Soc., Vol. 52, No. 3, pp. 216–242, 2004。
- Jussi 的表述与之吻合："Apodizing filters can fix problems in the source data, caused by decimation anti-alias filters in the recording"（[p/892506](https://community.roonlabs.com/p/892506)）。
- **HQPlayer 的 poly-sinc 家族思路**（据手册与作者帖归纳，非逐字引用）：
  - poly-sinc = **多项式窗**加权的 windowed-sinc（区别于常见的 Kaiser/Blackman 窗），窗形决定"过渡带宽度 vs 时域振铃"的取舍；
  - -2s = 两级实现（先到中间率再到目标率），用算力换实时性；这正好对应我们"两段式升频"的待办；
  - -mp = 最小相位版本；-lp = 线性相位；
  - -short / -long / -xl / -ext2 / -gauss 是不同的窗宽与窗形：窗越宽 → 过渡带越窄、阻带越深，但振铃越长；
  - **gauss 家族**用高斯窗，时域最"紧凑"，代价是过渡带更缓；
  - 新版用 **(a)** 后缀表示切趾变体（如 poly-sinc-gauss-xl(a)）。
- 更实用的一点：**HQPlayer 会统计"源素材里检测到多少需要切趾的错误"**，并把它做成一个计数指标（[p/1022968](https://community.roonlabs.com/p/1022968)）——"这个指标是告诉你何时需要切趾滤波器，而不是自动帮你选"。这是可以借鉴的产品化思路。

**证据等级**：A（JAES 论文 + 冲激/频响可测量）；具体听感差异的强弱属 B。

**我们能不能实现**：能，而且这是最值得做的部分。
- **1x / Nx 分开选滤波**（44.1k 源与 96k 源用不同窗宽）——功能成本低，收益明确；
- **切趾变体**：在现有 windowed-sinc 上加一个"混入 apodizing 修正"的选项（Craven 式：对通带边缘做平滑窗处理），并给出可测的冲激响应/群延迟对比；
- **切趾需求计数**：对源做"Nyquist 附近镜像能量/砖墙痕迹"的近似检测，作为提示而非自动决策；
- **最小相位 ↔ 线性相位**已是现成开关，建议在 UI 上直接标注群延迟毫秒数（371 ms 这种数字比"mp/lp"更有说服力）。

**实现代价**：1x/Nx 分离 0.5–1 天；切趾变体 2–3 天（含测量）；切趾计数 3–5 天（研究性质，可延后）。

### 2.9 噪声整形（NS9 / LNS15 / Gauss1）与 dither 的选择依据

**结论**：**规则明确、可量化、必须按"输出位深 + 输出采样率 + DAC 类型"三要素选**。这是"低成本高确定性"的一项。

Jussi 的选型口径（原帖）：

- "Generally **TPDF or Gauss1** is good for many cases. For **R2R type DACs** (real PCM DACs), **LNS15 or NS9** is good choice for **≥ 352.8k** output rates."（[p/1855285](https://community.roonlabs.com/p/1855285)）
- "Set Dither to LNS15, NS9 or NS5. Set **DAC Bits to 15**, based on the measurements I've seen."（R2R 具体案例，[p/1969954](https://community.roonlabs.com/p/1969954)）
- "If you use noise-shaped dither like LNS15 or NS9 **and high enough output rate** (at least 352.8k, preferably 705.6/768k), you have **more audio band dynamic range than TPDF dithered 24-bit**, and less distortion."（[p/289917](https://community.roonlabs.com/p/289917)）
- "Using LNS15 or NS9 gives you better linearity correction… 20-bit is 120 dB DNR, plus 12 dB from extra bandwidth = 132 dB in audio band."（[p/1809720](https://community.roonlabs.com/p/1809720)）
- NS9 的手册描述：**九阶噪声整形，专为 4× 速率（176.4/192 kHz）设计**，"非常激进"。

整理成我们的选型表：

| 输出 | 位深 | 建议 | 理由 |
|---|---|---|---|
| PCM 44.1/48k | 16-bit | NS 类整形（NS5–NS9 量级） | 带内 SNR 提升 10–20 dB 量级，噪声推到 20 kHz 以上 |
| PCM 88.2/96k | 16-bit | NS（阶数可降） | 整形带随 Fs 上移，注意 NTF 必须按 Fs 重标定 |
| PCM 176.4/192k | 16/24-bit | NS9（手册明示适用 4×） | 整形带已远离可闻区 |
| PCM ≥352.8k | 16–24-bit | **LNS15**（R2R）/ TPDF（ΔΣ DAC） | 高倍率下整形收益最大；ΔΣ DAC 内部还会再调制，扁平抖动更安全 |
| PCM 32-bit int/float | — | **不加抖动**（只做舍入） | 量化误差已埋进热噪声 |
| DSD | — | 由调制器承担整形，不额外 dither | 1-bit 的整形就是调制器本身 |

**证据等级**：A（作者选型口径 + 噪声整形论文 + 带内噪声可测量）。

**我们能不能实现**：基本已具备（NS9/LNS15 已有），待补：
1. **按输出采样率重标定 NTF**（本项目已知缺口：高采样率下整形带位置偏移）；
2. **按位深/采样率/DAC 类型自动选**，并在 UI 显示"当前 SNR 增益估算"；
3. **DAC Bits 手动上限**（R2R 用户按实测线性度设 15–20 bit，我们目前没有这个概念）。

**实现代价**：自动选型 0.5 天；NTF 重标定 2–3 天（需测量验证：用 --analyze 统计带内噪声与 THD+N）。

**参考**：Lipshitz, Wannamaker, Vanderkooy, *Minimally Audible Noise Shaping*, JAES 39(11):836–852, 1991；SoX 的 dither/噪声整形实现与其文档（[sox.sourceforge.net](https://sox.sourceforge.net/sox.html)）可作工程参照。

### 2.10 "玄学"与"可测"的分界

**能被测量/ABX 复现的（真实）**：

| 现象 | 为什么真实 | 怎么证 |
|---|---|---|
| 缓冲过小 → 爆音/丢样 | 调度抖动超过周期 | 欠载计数、事件超时 |
| 热母带的 inter-sample over | 重建波形在采样点之间超过 0 dBFS，DAC 定点满幅削顶 | 过采样后峰值统计 > 1.0 |
| 不同滤波器的差异 | 冲激响应/群延迟/过渡带确实不同 | 频响、冲激、ABX |
| 不同 dither/整形的差异 | 带内噪声底与失真不同 | 带内噪声积分、THD+N |
| 地环路/RF 耦合 | 模拟域真实存在的电流路径 | 噪声底测量（用 Cosmos ADC 之类） |
| 电平不匹配 | 0.1 dB 就足以"听出区别" | 电平校准后 ABX 复测 |
| DAC 内部 PLL 开关 | Jussi：抖动变化"数十 dB" | DAC 的 J-test |

**未证实/与物理矛盾的（玄学）**：

| 说法 | 判定 | 依据 |
|---|---|---|
| 比特相同的两个播放器声音不同 | D（除电气耦合外无通路） | 空转比对；Jussi"数字域无时钟"论述 |
| USB 线/网络交换机改变音质 | D（USB 异步 + DAC 拥有主时钟） | Jussi [p/1137671](https://community.roonlabs.com/p/1137671)；ASR 实测线材差异在噪声底之下（[ASR 帖](https://www.audiosciencereview.com/forum/index.php?threads/headphone-cables-whats-important-and-whats-not.5872/)） |
| CPU 频率越高声音越好 | D | 无机制；仅影响能否实时 |
| 定时器精度改变"声场/解析" | D | 事件驱动本就不用定时器 |
| MMCSS 劣化音质 | D | 与微软文档/van Eerde 相反，无对照 |
| event 更"线条"、push 更"厚" | D | 同一串样本，仅定时方式不同 |
| 内存速度/大页提升音质 | C/D | 只有吞吐影响 |
| 降频/关睿频"更纯净" | C | 机制（开关噪声降低）成立，但无受控实验 |
| 线材"煲"、软件"煲" | D | 无可测变化 |

**ABX 的正确做法**（否则测了也白测）：
1. 电平匹配到 ±0.1 dB（用粉噪测）；
2. 切换无爆音、无延迟差（延迟差本身会被听成"不同"）；
3. 至少 10 次，随机化，双盲；
4. 记录"差异描述"之前先记录"有没有差异"。

### 明确不做（以及为什么）

| 不做 | 原因 |
|---|---|
| 再调 MMCSS / TIME_CRITICAL / timeBeginPeriod | 已达成；Jussi 与 van Eerde 都反对继续加码 |
| 改 BIOS 关 C-State/SpeedStep/睿频 | 收益不可测，代价（功耗/稳定性）明确，且不可回滚验证 |
| 关 VBS/内核隔离 | 安全换性能，与音质无关 |
| 程序自动改 MSI 注册表 | 可能让设备不启动；只做检测与提示 |
| 追求更深的阻带（−189 → −249 dB） | 本项目已确认：−120 dB 以下对听感零意义 |
| 为"更好听"而加大缓冲 | 大缓冲只降低爆音概率，不改变声音 |
| USB 线材/网络"净化器"类优化 | 数字域无通路；除非做电气隔离（光纤以太网） |
